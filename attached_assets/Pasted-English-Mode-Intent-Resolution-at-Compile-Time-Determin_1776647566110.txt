Abstract
Natural-language programming interfaces promise to eliminate the cognitive distance between human intention and computational execution, but every existing implementation relies on probabilistic interpretation—neural language models, statistical parsers, or heuristic pattern matchers—that introduces irreducible variance into the compilation pipeline. When the same English sentence is interpreted twice by a probabilistic system, there is no guarantee that the second interpretation matches the first. This variance is tolerable for conversational assistants and code suggestion tools, but it is categorically incompatible with the deterministic execution, certificate-anchored provenance, and governance-constrained autonomy that the Lume ecosystem requires. I present English Mode Intent Resolution at Compile Time, a deterministic natural-language compilation pipeline that transforms unconstrained English prose into canonical Abstract Syntax Trees through a six-stage resolution process: lexical normalization, semantic grounding, constraint extraction, intent tuple formation, canonical AST mapping, and certificate-bound validation.

The pipeline operates entirely at compile time, producing a fully resolved, cryptographically sealed Intent Tuple before any runtime execution begins. Each resolution stage is deterministic: identical English input produces identical intermediate representations at every stage and identical final AST output across all compilations, regardless of the platform, the time of day, or the number of prior compilations. The pipeline integrates with the Lume compiler through the LDIR seven-layer tolerance chain [1], with the Trust Layer Certificate Fabric [3] through compile-time certificate emission, with Lume-V [4] through envelope constraint derivation, with DAIGS [5] through cognitive substrate integration, and with GUPAS [2] through the six-layer governance architecture. I also identify and formalize six failure modes—ambiguity collapse, over-specification, under-specification, conflicting constraints, semantic drift, and intent inversion—that deterministic natural-language compilers must detect and resolve at compile time rather than deferring to runtime heuristics. To my knowledge, this paper presents the first complete compile-time intent resolution pipeline for natural-language programming that provides bit-identical deterministic output with cryptographic provenance guarantees.

1 Introduction
1.1 The Rise of Natural-Language Programming
The aspiration to program computers using natural language is as old as programming itself. From COBOL's English-like syntax in the 1960s through AppleScript's natural-language scripting in the 1990s to the contemporary explosion of large language model-based code generation tools, the field has pursued the elimination of syntactic barriers between human thought and computational execution [12]. Each generation of natural-language programming tools has expanded the boundary of what can be expressed in human-readable form, but each generation has also inherited a fundamental architectural assumption: that natural-language understanding requires probabilistic inference.

This assumption is so deeply embedded in the field that it is rarely questioned. Natural language is ambiguous; therefore, understanding natural language requires resolving ambiguity; therefore, resolving ambiguity requires probabilistic reasoning about the most likely intended meaning. The conclusion seems inescapable: natural-language programming must involve a probabilistic interpretation stage that introduces irreducible variance into the compilation pipeline. Two compilations of the same English sentence may produce different executable outputs if the probabilistic model's internal state has changed between compilations.

The Lume programming language challenges this assumption at the architectural level [1]. Lume demonstrates that natural-language expressions can be compiled through a deterministic pipeline that produces bit-identical outputs for bit-identical inputs, without any probabilistic inference stage. The mechanism is the seven-layer tolerance chain, which resolves ambiguity through an ordered, deterministic rule cascade rather than through statistical likelihood estimation. This mechanism transforms natural-language compilation from a probabilistic process into a deterministic function.

English Mode is the user-facing manifestation of this deterministic natural-language compilation capability. When a programmer activates English Mode, they write unconstrained English prose that the Lume compiler transforms into executable code through the same deterministic pipeline used for Lume's structured syntax. The programmer does not need to learn Lume's keyword vocabulary or syntactic conventions; they express their intent in the language they already know, and the compiler resolves that intent into deterministic computation. This paper formalizes the intent resolution pipeline that makes English Mode possible.

1.2 Why English Mode Requires Deterministic Compilation
The requirement for deterministic compilation in English Mode is not a preference but a structural necessity imposed by the Lume ecosystem's architecture. Every compiled Lume program receives a Certified-at-Birth certificate chain that binds the source hash, the AST hash, and the output hash to the compiler's identity [1]. This certificate chain constitutes mathematical proof that a specific source expression produced a specific executable through a specific compilation process. If the compilation process were nondeterministic, the certificate would be meaningless: the same source expression could produce multiple different executables, and the certificate would attest to a relationship that holds for one execution but not another.

Deterministic compilation is also essential for the GUPAS governance architecture [2]. GUPAS governs autonomous software through pre-execution validation: the governance layer verifies that a proposed action will comply with policy constraints before the action is executed. This pre-execution validation depends on the assumption that the same intent always produces the same action. If English Mode compilation were nondeterministic, pre-execution validation would be unreliable—the governance layer might approve an action based on one compilation, but the actual execution might follow a different compilation path that violates the approved policy.

The Trust Layer Certificate Fabric [3] imposes a further requirement: certificate chain integrity. Every certificate in the Trust Layer chains to its parent through hash linkage. If the compilation process produces different AST hashes for the same input, the certificate chain fragments: different compilations produce different chains that cannot be reconciled. Deterministic compilation ensures that the certificate chain is singular—one input, one AST, one hash, one chain—providing a clean, unambiguous provenance trail from English prose to executable code.

The zero-knowledge state reversal protocol [8] depends on deterministic compilation for reversal verification. When a state is rolled back, the reversal proof must demonstrate that the rolled-back state is mathematically equivalent to a previously committed state. If the program that produced the committed state was compiled nondeterministically, the reversal proof cannot verify equivalence because re-compilation might produce a different program. Deterministic compilation ensures that re-compilation always produces the identical program, enabling mathematically precise reversal verification.

1.3 The Gap Between Human Language and Machine Determinism
Human language and machine determinism occupy opposite ends of the expressiveness-precision spectrum. Human language is optimized for communicative efficiency between beings that share vast amounts of contextual knowledge, cultural common ground, and embodied experience. Speakers routinely use ambiguous pronouns, implicit references, context-dependent idioms, and elliptical constructions because their listeners can resolve these ambiguities through shared context. Machine execution is optimized for precision: every instruction must specify its operation, its operands, and its effects without relying on contextual inference.

The gap between these two modes of expression has historically been bridged by programmers—human beings who understand both human intent and machine requirements and who manually translate between the two. Programming languages provide structured vocabularies that constrain human expression to forms that can be mechanically translated into machine instructions. The programmer sacrifices some natural expressiveness in exchange for the guarantee that their expression will be interpreted consistently.

English Mode attempts to close this gap without requiring the programmer to sacrifice natural expressiveness. The programmer writes in unconstrained English, and the compiler takes responsibility for resolving the ambiguities that English introduces. The critical innovation is that the compiler resolves these ambiguities deterministically—not by guessing the most likely meaning but by applying a fixed set of resolution rules in a fixed order, producing a deterministic outcome for any given input. The rules are designed to produce sensible outcomes for well-formed English expressions, but their primary guarantee is not sensibility; it is determinism.

This design choice has an important consequence: English Mode's resolution of an ambiguous expression may not always match what a human reader would consider the "most natural" interpretation. The resolution instead matches what the deterministic rule cascade specifies for that particular syntactic pattern. Programmers working in English Mode learn the resolution conventions just as programmers working in any language learn its semantic conventions. The difference is that English Mode's input format is natural English rather than a specialized syntax.

1.4 Relationship to Lume, Trust Layer, DAIGS, LDIR, and GUPAS
English Mode operates within the Lume compiler as an alternative input frontend. The compiler's standard frontend accepts Lume structured syntax; the English Mode frontend accepts unconstrained English prose. Both frontends produce identical internal representations—canonical ASTs—that are processed through the same downstream pipeline (optimization, code generation, certification). The English Mode frontend is not a separate compiler; it is an alternative entry point into the same deterministic compilation pipeline.

The Trust Layer [3] provides the certification infrastructure that anchors English Mode compilations to the Certificate Fabric. When English Mode resolves an English expression into a canonical AST, the resolution process emits a resolution certificate that records the input text, the intermediate representations at each resolution stage, and the final AST hash. This certificate enables any participant to verify that a specific English expression was compiled into a specific program through a specific resolution path.

DAIGS [5] provides the cognitive substrate that English Mode leverages for compound intent resolution. When an English expression contains multiple intents ("create a file, write the contents, and send it to the server"), the DAIGS cognitive substrate coordinates the resolution of each sub-intent and manages the dependencies between them. LDIR provides the inference rulebook that governs how ambiguous English constructs are resolved into unambiguous computational directives. GUPAS [2] provides the governance framework within which English Mode compilations are validated against policy constraints before execution proceeds.

1.5 Overview of Contributions
This paper makes five primary contributions. First, I define the six-stage intent resolution pipeline that transforms unconstrained English prose into canonical ASTs through deterministic semantic grounding. Second, I formalize the compile-time intent arbitration mechanism that resolves competing interpretations of ambiguous English expressions through the LDIR rule cascade. Third, I identify and classify six failure modes specific to deterministic natural-language compilation, providing detection criteria and resolution strategies for each. Fourth, I specify the integration architecture between English Mode and each component of the Lume ecosystem (Lume compiler, Trust Layer, Lume-V, DAIGS, LDIR, GUPAS). Fifth, I provide security analysis demonstrating that the English Mode pipeline resists intent tampering, semantic manipulation, and governance abuse.

The significance of this paper extends beyond its technical contributions to the field of human-computer interaction. English Mode demonstrates that the barrier between human expression and deterministic computation can be crossed without sacrificing the guarantees that make deterministic systems trustworthy. The CHI community has long studied the design of programming interfaces that reduce cognitive distance [13]; English Mode eliminates cognitive distance entirely by accepting the programmer's native language as the input format. The formalization presented here provides the theoretical foundation for this capability.

2 Foundations of English Mode
2.1 Natural-Language Determinism
Natural-language determinism is the property that a deterministic function can transform a natural-language expression into a computational representation such that identical expressions always produce identical representations. This property contradicts the assumption, prevalent in computational linguistics, that natural-language understanding necessarily involves probabilistic inference [14]. The assumption arises from the observation that natural language is ambiguous and that resolving ambiguity requires choosing among multiple possible interpretations. Probabilistic systems choose the most likely interpretation; deterministic systems choose the interpretation specified by a fixed rule cascade.

The Lume compiler achieves natural-language determinism through the seven-layer tolerance chain [1]. The chain processes input through an ordered sequence of resolution strategies: exact pattern match, fuzzy pattern match (edit distance ≤ 2), sentence splitting for compound intents, pronoun resolution using a context stack, temporal sequencing for multi-step intents, logic block detection for conditional intents, and normalized AI fallback for expressions that no prior layer resolves. Each layer produces a deterministic output for any given input, and the chain terminates at the first layer that produces a successful resolution.

The key insight is that determinism does not require understanding in the cognitive sense. The compiler does not "understand" the English expression; it applies pattern matching and rule evaluation to transform the expression into a structured representation. The transformation is mechanical, reproducible, and verifiable. Whether the transformation captures the programmer's "true intent" is a separate question—one that is addressed through the feedback mechanisms built into the English Mode workflow (preview, confirmation, and iterative refinement).

Natural-language determinism is a stronger property than mere consistency. A probabilistic system can be consistent if its random seed is fixed, but this consistency is fragile: changing the model version, the hardware, or the inference parameters may alter the output. Natural-language determinism as implemented in Lume is structural: the resolution function is a mathematical object whose behavior is fully specified by its rules and their ordering. No model weights, no random seeds, no inference parameters influence the output.

2.2 Intent as a Computational Substrate
In the Lume architecture, intent is not a transient mental state that disappears during compilation. Intent is a persistent, structured data object—the Intent Tuple—that propagates through every phase of the compilation and execution lifecycle [2]. The Intent Tuple binds five fields: the intent source (the original English expression), the intent hash (SHA3-256 digest of the canonicalized source), the resolved action (the deterministic interpretation produced by the LDIR tolerance chain), the trust binding (the certificate anchoring the intent to an identity), and the envelope constraint (the safety boundary within which the intent may be executed).

English Mode's primary function is to populate the Intent Tuple from unconstrained English prose. The six-stage resolution pipeline (§4) transforms the English expression into each of the Intent Tuple's fields through a deterministic process. The intent source field captures the original expression. The intent hash field is computed from the canonicalized form of the expression (whitespace-normalized, case-folded, punctuation-standardized). The resolved action field is produced by the semantic grounding and constraint extraction stages. The trust binding field is produced by the certificate-bound validation stage. The envelope constraint field is derived from the constraint extraction stage's analysis of the expression's resource implications.

The treatment of intent as a computational substrate has direct implications for English Mode's design. Because the Intent Tuple must survive the entire execution lifecycle—through arbitration, delegation, healing, reversal, and certification—the English Mode pipeline must produce Intent Tuples that are complete, self-contained, and unambiguous. An Intent Tuple that contains unresolved ambiguity would propagate that ambiguity through the entire lifecycle, undermining the deterministic guarantees at every downstream stage.

2.3 Semantic Normalization
Semantic normalization is the process of transforming diverse English expressions that convey the same computational intent into a single canonical form. The English language provides many ways to express the same action: "create a file called report.txt," "make a new file named report.txt," "generate a file with the name report.txt," and "produce a file titled report.txt" all express the same computational intent. Semantic normalization maps all four expressions to the identical canonical form: CREATE_FILE(name="report.txt").

The normalization process operates in three phases. The first phase is verb normalization: English verbs are mapped to canonical action verbs through a verb synonym table. "Create," "make," "generate," "produce," "build," and "construct" all map to the canonical verb CREATE. "Delete," "remove," "destroy," "eliminate," and "erase" all map to the canonical verb DELETE. The verb synonym table is version-locked to the LDIR rulebook version and is loaded as a read-only data structure at compiler initialization.

The second phase is parameter normalization: English phrases describing parameters are mapped to canonical parameter structures. "Called report.txt," "named report.txt," "with the name report.txt," and "titled report.txt" all map to the canonical parameter name="report.txt". Parameter normalization uses a combination of preposition analysis ("called," "named," "with the name") and positional analysis (the value immediately following the preposition) to extract parameter values deterministically.

The third phase is structural normalization: compound English sentences are decomposed into sequences of atomic canonical operations. "Create a file called report.txt and write the quarterly earnings summary to it" is decomposed into two atomic operations: CREATE_FILE(name="report.txt") followed by WRITE_FILE(target="report.txt", content="quarterly earnings summary"). The decomposition follows the sentence's syntactic structure (conjunction analysis) and the LDIR's temporal sequencing rules (Layer 5 of the tolerance chain).

2.4 Canonical AST Generation
Canonical AST generation transforms the normalized intent representation into the deterministic Abstract Syntax Tree format defined by the Lume compiler specification [6]. The canonical AST follows a strict construction order—depth-first, left-to-right, following canonical reading order—ensuring that the same intent always produces the same tree structure. The AST node vocabulary includes Program, Command, Sequence, Condition, Block, List, Value, Identifier, ModuleCall, Parameter, Comparison, LogicalExpression, and TemporalExpression.

English Mode's AST generation maps each canonical action (produced by semantic normalization) to the appropriate AST node type. A file creation action maps to a Command node with a ModuleCall child referencing the file system module. A conditional action maps to a Condition node with comparison children. A temporal sequence maps to a TemporalExpression node with ordered step children. The mapping is specified in a static action-to-AST table that is version-locked to the compiler version.

The generated AST is hashed using SHA3-256 following the canonical serialization protocol: the tree is serialized depth-first, left-to-right, with each node's type, value, and child count encoded in a fixed binary format. This hash becomes the AST component of the Intent Tuple and is bound to the compilation certificate. Any modification to the AST—whether through optimization, healing, or tampering—changes the hash and breaks the certificate chain.

2.5 Envelope-Bound Semantics
English Mode compilation does not merely produce executable code; it produces executable code within a safety envelope. The envelope is derived from the English expression's semantic content through the constraint extraction stage (§4.3). When a programmer writes "read the sales data from the database," the constraint extraction stage identifies the implied resource requirements (database access) and interaction boundaries (read-only access) and encodes them as envelope parameters.

Envelope derivation from English prose is inherently conservative. When the English expression does not explicitly specify a resource limit, the compiler applies the default envelope from the execution context. When the English expression implies a resource requirement that exceeds the execution context's envelope, the compiler emits a constraint violation warning at compile time, alerting the programmer before any runtime execution occurs. This compile-time envelope validation is a direct benefit of performing intent resolution at compile time rather than at runtime.

The envelope-bound semantics ensure that English Mode code operates within the same safety framework as Lume structured-syntax code and Lume-V wrapped code [4]. The envelope constraints compose through the same set intersection rule used throughout the GUPAS architecture: the English Mode envelope is the intersection of the expression-derived envelope and the execution context's envelope, producing the most restrictive combined boundary.

3 The Challenge of Natural-Language Compilation
3.1 Ambiguity and Semantic Drift
Ambiguity is the defining challenge of natural-language compilation. English sentences admit multiple syntactic parses, multiple semantic interpretations, and multiple pragmatic implications. The sentence "time flies like an arrow" has at least three valid parses: a metaphorical assertion (time passes quickly), an imperative command (measure the speed of flies in the manner of an arrow), and a descriptive statement (temporal flies are fond of arrows). A probabilistic compiler selects among these parses based on statistical likelihood; a deterministic compiler must select among them based on fixed rules.

Semantic drift compounds the ambiguity problem over time. The meaning of English words shifts across contexts, communities, and generations. "Server" meant a person who serves food before it meant a networked computer. "Cloud" meant a meteorological phenomenon before it meant a distributed computing infrastructure. A deterministic compiler must be robust against semantic drift, mapping words to canonical meanings through a version-locked vocabulary rather than relying on contemporary usage statistics that may shift between compiler versions.

English Mode addresses ambiguity and semantic drift through the LDIR's ordered tolerance chain. The chain's layered structure ensures that the most precise resolution strategy is tried first (exact pattern match), with progressively more flexible strategies tried only when more precise strategies fail. This ordering ensures that unambiguous expressions are resolved immediately, while ambiguous expressions are resolved through the most specific applicable resolution rule. The version-locked vocabulary ensures that word-to-meaning mappings are fixed at compiler release and do not drift between compilations.

3.2 Contextual Overload
Natural language relies heavily on context to resolve references and determine meaning. The pronoun "it" in "create a file and write to it" refers to the file created in the first clause. The determiner "the" in "read the database" presupposes that a specific database has been established in the prior context. Context resolution requires maintaining a context stack that tracks the entities, actions, and relationships introduced by prior expressions.

Contextual overload occurs when the context stack becomes too deep or too complex for deterministic resolution. If a sequence of English expressions introduces dozens of entities with overlapping attributes, the pronoun resolution logic may face multiple equally valid referents. In probabilistic systems, this ambiguity is resolved through statistical co-reference resolution. In English Mode, this ambiguity triggers a deterministic fallback: the compiler selects the most recently introduced entity that matches the pronoun's syntactic constraints (number, gender where applicable), following the LDIR's pronoun resolution rules (Layer 4 of the tolerance chain).

The context stack is bounded to prevent unbounded growth. English Mode maintains a fixed-size context window (configurable, default 16 entities) that retains the most recently introduced entities. Entities that fall outside the context window are no longer available for pronoun resolution and must be referenced by name. This bounding ensures that the context resolution logic operates in constant time relative to the window size, preventing performance degradation in long English Mode sessions.

3.3 Probabilistic Interpretation Pitfalls
Probabilistic interpretation systems—including large language models, statistical parsers, and neural machine translation systems—suffer from three fundamental pitfalls that make them unsuitable for deterministic compilation. The first pitfall is reproducibility failure: the same input may produce different outputs across model versions, hardware platforms, or inference configurations, because the statistical inference process depends on floating-point arithmetic that is sensitive to platform-specific optimizations.

The second pitfall is distributional bias: probabilistic systems tend to favor interpretations that appear frequently in their training data, regardless of whether those interpretations are correct for the specific compilation context. A financial term that is rare in general English but common in financial programming may be misinterpreted because the statistical model's prior is dominated by non-financial contexts. Deterministic compilation avoids this pitfall by using a domain-specific vocabulary that maps terms to canonical meanings independent of their general-English frequency.

The third pitfall is adversarial vulnerability: probabilistic interpretation systems are susceptible to adversarial inputs that exploit the statistical model's weaknesses to produce attacker-controlled outputs [15]. An attacker can craft English expressions that appear benign to human readers but trick the probabilistic model into producing malicious code. Deterministic compilation is immune to this attack vector because the resolution process follows fixed rules rather than learned weights—an attacker cannot influence the resolution outcome by crafting inputs that exploit statistical biases that do not exist in the deterministic system.

3.4 Deterministic Constraints
Deterministic natural-language compilation operates under constraints that are absent from probabilistic systems. The canonical ordering constraint requires that the AST construction follows a fixed traversal order. The hash binding constraint requires that the AST hash is computed from a canonical serialization that is invariant across platforms. The certificate chain constraint requires that every compilation produces a certificate chain that links the English source to the executable output through verifiable, tamper-evident hash bindings.

These constraints collectively ensure that English Mode compilation is a mathematical function: a mapping from the space of English expressions to the space of canonical ASTs that satisfies the uniqueness property (each input maps to exactly one output), the determinism property (the mapping is invariant across invocations), and the verifiability property (the correctness of the mapping can be independently verified through the certificate chain). Conventionally, these properties are associated with formal languages, not natural languages. English Mode achieves them for a subset of English by constraining the resolution process rather than constraining the input language.

The constraints impose a trade-off: English Mode may reject English expressions that a probabilistic system would accept. When the LDIR tolerance chain exhausts all seven layers without producing a resolution, the compiler emits a HALT rather than guessing. This rejection is a feature, not a limitation: the programmer receives explicit feedback that their expression was not resolvable, enabling them to rephrase the expression in a form that the compiler can resolve deterministically. The alternative—accepting every expression and silently guessing the meaning—would undermine the deterministic guarantee on which the entire ecosystem depends.

4 The Intent Resolution Pipeline
4.1 Lexical Normalization
Lexical normalization is the first stage of the intent resolution pipeline. It transforms the raw English input into a standardized lexical representation by applying four deterministic transformations: whitespace normalization (collapsing multiple spaces, tabs, and newlines into single spaces), case folding (converting all characters to lowercase for matching purposes while preserving the original case for display), punctuation standardization (mapping typographic variants to canonical punctuation), and encoding normalization (converting all text to UTF-8 NFC form).

Lexical normalization also performs contraction expansion ("don't" → "do not," "can't" → "cannot," "it's" → "it is") and abbreviation resolution ("DB" → "database," "API" → "application programming interface," "URL" → "uniform resource locator"). The contraction and abbreviation tables are version-locked to the compiler version, ensuring that the expansion is deterministic across compilations. Domain-specific abbreviations can be registered through the Semantic Expansion Subsystem [10] for specialized compilation contexts.

The lexical normalization stage produces a normalized token stream that serves as input to the semantic grounding stage. Each token in the stream carries its normalized form, its original form, its position in the source text, and its character span in the original input. This positional metadata enables subsequent stages to generate error messages that reference the original English text rather than the normalized form, providing the programmer with actionable feedback.

4.2 Semantic Grounding
Semantic grounding transforms the normalized token stream into a structured semantic representation by mapping English words and phrases to canonical meaning structures. The grounding process operates through three sub-stages: verb identification (locating the action verbs in the token stream), object identification (locating the entities acted upon), and modifier identification (locating the adverbs, adjectives, and prepositional phrases that qualify the action).

Verb identification uses the verb synonym table to map English verbs to canonical action verbs. The table maps over 500 English verbs to a core set of 47 canonical actions (CREATE, READ, UPDATE, DELETE, SEND, RECEIVE, COMPUTE, COMPARE, SORT, FILTER, and others). When an English verb appears in the token stream, the grounding stage looks up the verb in the synonym table and replaces it with the canonical action. If the verb is not in the table, the grounding stage attempts fuzzy matching (edit distance ≤ 2) before escalating to the AI fallback layer.

Object identification extracts the entities that the canonical action operates on. The grounding stage identifies noun phrases following the action verb and maps them to canonical object types (FILE, DATABASE, VARIABLE, LIST, NETWORK_ENDPOINT, MODULE). The mapping uses a combination of keyword recognition ("file," "database," "variable") and contextual inference (a noun phrase following CREATE that is not a recognized keyword is treated as a VARIABLE name by default).

Modifier identification extracts the qualifications that constrain the action. Adverbs ("quickly," "safely," "quietly") are mapped to execution modifiers (execution priority, safety level, logging verbosity). Prepositional phrases ("to the server," "from the database," "with encryption") are mapped to parameter bindings (destination, source, processing mode). The modifier mapping follows the same deterministic table-lookup approach used for verb and object identification.

4.3 Constraint Extraction
Constraint extraction analyzes the semantically grounded representation to derive the envelope constraints and preconditions that the English expression implies. The extraction process identifies four categories of constraints: resource constraints (the computational resources the action will consume), scope constraints (the state regions the action will modify), interaction constraints (the external systems the action will contact), and temporal constraints (the time boundaries within which the action must complete).

Resource constraints are derived from the canonical action's resource profile. Each canonical action has a pre-computed resource profile that specifies its expected CPU consumption, memory allocation, and network bandwidth. The CREATE_FILE action, for example, requires disk I/O bandwidth and file system metadata allocation. The COMPUTE action requires CPU cycles proportional to the input data size. These profiles are combined with the intent's parameters to estimate the action's total resource requirements.

Scope constraints are derived from the canonical action's state mutation specification. Each canonical action specifies which state regions it may modify: CREATE_FILE modifies the file system, UPDATE modifies the target variable, SEND modifies the network buffer. The constraint extraction stage maps these specifications to envelope parameters, enabling the GUPAS Envelope layer to validate the action against the agent's authorized state mutation scope before execution.

Temporal constraints are either explicitly stated in the English expression ("within 5 seconds," "before the deadline") or implicitly derived from the execution context's default temporal limits. Explicit temporal constraints are parsed through the LDIR's temporal sequencing logic (Layer 5 of the tolerance chain). Implicit temporal constraints are inherited from the agent's envelope certificate. The more restrictive of the explicit and implicit constraints applies, following the envelope intersection rule.

4.4 Intent Tuple Formation
Intent tuple formation assembles the outputs of the preceding stages into the canonical Intent Tuple data structure. The formation process binds the original English expression (intent source), the SHA3-256 hash of the canonicalized expression (intent hash), the semantically grounded and constraint-extracted action specification (resolved action), the compiler's identity certificate (trust binding), and the derived envelope constraints (envelope constraint) into a single, immutable data structure.

The Intent Tuple's immutability is enforced through hash sealing: once the tuple is formed, its complete content is hashed and the hash is bound to the compilation certificate. Any subsequent modification to any field of the tuple changes the hash and invalidates the certificate. This sealing occurs at compile time, before any runtime execution, ensuring that the Intent Tuple that reaches the runtime is the exact tuple that was produced by the compilation pipeline.

The formation stage also validates the internal consistency of the tuple. The resolved action must be compatible with the envelope constraints: an action that requires network access cannot be bound to an envelope that prohibits network access. The trust binding must be valid: the compiler's certificate must be current and unrevoked. The intent hash must match the canonicalized source: recomputing the hash from the source and comparing it to the stored hash verifies that no corruption occurred during the normalization process. Any inconsistency detected during formation triggers a compile-time error.

4.5 Canonical AST Mapping
Canonical AST mapping transforms the resolved action specification from the Intent Tuple into the deterministic Abstract Syntax Tree that the Lume runtime will execute. The mapping follows the action-to-AST table, which specifies the AST node structure for each canonical action. The CREATE_FILE action maps to a Command node containing a ModuleCall node referencing the file system module, with Parameter children specifying the file name and initial contents.

The AST mapping handles compound intents by generating Sequence nodes that contain the individual action ASTs in the order specified by the temporal sequencing logic. A compound intent such as "create a file and write to it" produces a Sequence node containing two Command children: the file creation command and the file write command, ordered by their implicit temporal dependency (creation before writing).

Conditional intents ("if the file exists, update it; otherwise, create it") are mapped to Condition nodes with Comparison children and Block children. The Comparison child evaluates the condition (file existence check), and the Block children contain the conditional action ASTs (update or create). The mapping follows the LDIR's logic block detection rules (Layer 6 of the tolerance chain), which identify conditional constructs in the semantically grounded representation.

4.6 Certificate-Bound Validation
Certificate-bound validation is the final stage of the intent resolution pipeline. It produces the compilation certificate that binds the English source to the canonical AST through the Trust Layer Certificate Fabric [3]. The validation stage generates a COMPILE_ROOT certificate containing the source hash, the AST hash, the output hash, the compiler identity, the resolution path (which layers of the tolerance chain were used), and the derived envelope constraints.

The certificate-bound validation also verifies the compilation against the Trust Layer's governance policies. If the compilation context includes governance constraints (such as a prohibition on file deletion or a requirement for encryption on network communications), the validation stage checks whether the compiled action violates any constraint. Violations are reported as compile-time governance errors, providing immediate feedback to the programmer.

The completed certificate is appended to the compiled artifact, creating a self-documenting executable that carries its own provenance trail. Any recipient of the compiled artifact can verify the certificate chain, confirming that the artifact was compiled from a specific English expression by a specific compiler instance within a specific governance context. This verification does not require access to the compiler or to the original English expression; the certificate provides sufficient information for independent verification.

5 Compile-Time Intent Arbitration
5.1 Competing Interpretations
When the LDIR tolerance chain evaluates an ambiguous English expression, it may encounter multiple resolution candidates at the same tolerance layer. The expression "set the value to maximum" could resolve to an assignment operation (SET variable TO maximum_constant) or to an optimization operation (MAXIMIZE the value parameter). When the semantic grounding stage identifies multiple valid canonical actions for the same English expression, the compile-time intent arbitration mechanism activates.

Competing interpretations arise from three sources: verb polysemy (a single English verb mapping to multiple canonical actions), structural ambiguity (a single sentence admitting multiple syntactic parses), and contextual ambiguity (a pronoun or determiner with multiple valid referents). The intent arbitration mechanism handles all three sources through the same deterministic resolution process, ensuring consistent treatment regardless of the ambiguity's origin.

The arbitration mechanism operates entirely at compile time. The programmer does not experience runtime ambiguity; all ambiguity is resolved before the program executes. If the arbitration mechanism cannot resolve the ambiguity deterministically, the compiler emits a HALT with a diagnostic message explaining the competing interpretations and suggesting disambiguating rephrasings. This compile-time resolution is a fundamental advantage of English Mode over runtime interpretation approaches, which may select different interpretations on different executions.

5.2 Priority Rules
The intent arbitration mechanism resolves competing interpretations through priority rules derived from the LDIR rule hierarchy. The hierarchy assigns priority based on four factors: specificity (more specific interpretations are preferred over more general ones), precedence (earlier rules in the same tier are preferred over later rules), context (interpretations consistent with the current context stack are preferred over context-independent interpretations), and safety (interpretations with smaller envelope footprints are preferred over interpretations with larger footprints).

Specificity is the primary tiebreaker. An interpretation that matches an exact pattern in the verb synonym table takes priority over an interpretation that matches through fuzzy matching. An interpretation that resolves all parameters deterministically takes priority over an interpretation that leaves parameters to default values. This specificity preference ensures that the arbitration mechanism favors precise resolutions over vague ones.

Safety serves as the ultimate tiebreaker. When two interpretations are equally specific, equally precedent, and equally context-consistent, the interpretation with the smaller envelope footprint is selected. This safety preference ensures that ambiguity is resolved in favor of the least powerful operation, following the principle of least privilege. The programmer who intended the more powerful operation can disambiguate by providing additional specificity in the English expression.

5.3 Envelope Constraints
Envelope constraints participate in compile-time arbitration by eliminating interpretations that would violate the compilation context's safety boundaries. If the programmer's envelope prohibits network access, any interpretation that requires network access is eliminated from the candidate set before arbitration proceeds. This pre-arbitration filtering reduces the candidate set and frequently resolves ambiguity without requiring the priority rules.

The envelope constraint filtering is conservative: it eliminates only interpretations that would certainly violate the envelope, not interpretations that might violate the envelope under some circumstances. An interpretation that accesses the network conditionally (only if a certain condition holds) is not eliminated by envelope filtering; it passes through to the priority rules, where the conditional nature of the network access is evaluated in the context of the specific condition.

Envelope-aware arbitration provides a security benefit: it prevents the compiler from selecting interpretations that the programmer is not authorized to execute. A programmer with read-only file system access cannot accidentally trigger a file deletion interpretation, because file deletion is eliminated from the candidate set by the envelope constraint filter. This preventive mechanism operates at compile time, long before the potentially harmful action could reach the runtime.

5.4 Arbitration Certificates
Every arbitration decision is recorded in an Arbitration Certificate that is appended to the compilation certificate chain. The Arbitration Certificate records the competing interpretations that were considered, the priority rules that were applied, the envelope constraints that were evaluated, and the final selected interpretation. This certificate provides a complete, verifiable record of how the compiler resolved the ambiguity.

Arbitration Certificates enable retrospective analysis of compile-time decisions. If a programmer disputes the compiler's interpretation of an ambiguous expression, the Arbitration Certificate provides the evidence needed to understand the decision. The programmer can see which interpretations were considered, why each was accepted or rejected, and what the deciding factor was. This transparency is essential for building programmer trust in the deterministic compilation process.

The certificates also feed the Evolver's pattern-capture mechanism. The LDIR's global inference patterns track which arbitration decisions are most frequently made for common ambiguity patterns, informing the refinement of default resolution strategies for subsequent compiler versions. This feedback loop enables the English Mode pipeline to improve its resolution quality over time while maintaining strict determinism within any given compiler version.

5.5 Deterministic Finalization
Deterministic finalization is the process of committing the arbitration decision and producing the final, sealed Intent Tuple and canonical AST. Once the arbitration mechanism selects an interpretation, the selection is irreversible within the current compilation. The compiler does not revisit the decision, does not second-guess the arbitration, and does not allow subsequent stages to override the arbitration outcome.

Finalization produces three outputs: the sealed Intent Tuple (with all five fields populated and hash-bound), the canonical AST (constructed according to the deterministic construction order), and the compilation certificate chain (linking the English source through the resolution stages to the final executable). These three outputs constitute the complete compilation artifact—a self-documenting, self-verifying package that carries its provenance from human expression to machine instruction.

The finalization stage performs a final determinism verification: the compiler re-runs the lexical normalization stage on the original English input and compares the output hash against the hash recorded in the Intent Tuple. If the hashes match, the compilation is confirmed deterministic. If they differ (which would indicate a bug in the pipeline), the compilation is rejected and the discrepancy is reported. This end-to-end verification provides a built-in self-test that detects pipeline errors before they reach the programmer.

6 Integration with Lume
6.1 AST Determinism
English Mode produces the same canonical AST format as Lume's structured syntax frontend. The AST node vocabulary, the construction order, the serialization protocol, and the hash computation are identical across both frontends. This format identity ensures that downstream pipeline stages (optimization, code generation, runtime execution) cannot distinguish between ASTs produced from Lume structured syntax and ASTs produced from English Mode. The indistinguishability is deliberate: English Mode is an alternative input modality, not an alternative compilation target.

AST determinism across frontends enables a powerful verification technique: cross-compilation comparison. A programmer can express the same intent in both Lume structured syntax and English Mode and compare the resulting AST hashes. If the hashes match, the English Mode compilation produced the same program as the structured syntax compilation, confirming that the English expression is correctly interpreted. If the hashes differ, the programmer can examine the divergence to understand how the English Mode resolution differs from the intended interpretation.

The cross-compilation comparison technique also serves as a regression test for the English Mode pipeline. A corpus of English-to-Lume pairs, with verified equivalence, can be re-compiled after every pipeline update to detect regressions. Any pair that produces matching hashes before the update but divergent hashes after the update indicates a regression in the English Mode resolution logic.

6.2 Grammar Constraints
English Mode operates within grammar constraints that are derived from the Lume structured syntax but expressed in natural-language terms. The Lume grammar defines a fixed set of computational constructs (commands, sequences, conditions, blocks, module calls, expressions). English Mode maps natural-language patterns to these constructs through the semantic grounding stage. The grammar constraints ensure that English Mode can express exactly the computational constructs that Lume structured syntax can express—no more, no fewer.

This constraint parity eliminates the risk of English Mode introducing computational capabilities that bypass the Lume compiler's safety checks. If Lume structured syntax does not support a particular operation (such as arbitrary pointer arithmetic), English Mode cannot express that operation either. The grammar constraint mapping is defined in the action-to-AST table, which is version-locked to the compiler version and audited as part of the compiler's certification process.

Grammar constraints also prevent English Mode from producing ASTs that the Lume runtime cannot execute. Every AST node type produced by English Mode exists in the Lume runtime's supported node set. Every parameter combination produced by English Mode is within the runtime's accepted parameter ranges. This compatibility is guaranteed by construction: the action-to-AST table is derived from the same grammar specification that defines the Lume runtime's execution semantics.

6.3 Runtime Compatibility
English Mode compiled programs execute within the standard Lume runtime without modification. The runtime receives a canonical AST and executes it according to the standard deterministic execution semantics: no random number generation, no environment-dependent branching, no timing-dependent behavior [1]. The runtime does not know or care whether the AST was produced from Lume structured syntax or from English Mode; the execution is identical in either case.

Runtime compatibility extends to the SOR cell model. English Mode programs execute within SOR cells with the same memory isolation, fault containment, and lifecycle management as Lume structured-syntax programs. English Mode programs participate in the same Signal Bus communication, the same homeostatic regulation, and the same multi-agent coordination as structured-syntax programs. The English Mode frontend is transparent to the runtime layer.

This transparency is a critical design requirement for ecosystem coherence. If English Mode programs exhibited different runtime behavior than structured-syntax programs—different resource consumption patterns, different failure modes, different interaction semantics—the ecosystem would fragment into two incompatible execution models. Runtime compatibility prevents this fragmentation by ensuring that the choice of input modality has no effect on execution behavior.

6.4 Canonicalization Rules
Canonicalization rules govern the transformation of English Mode's intermediate representations into the canonical forms required by the Lume pipeline. The rules specify how normalized tokens map to AST identifiers, how semantic structures map to AST node types, and how constraint specifications map to envelope parameters. The rules are defined in a machine-readable specification document that is published alongside the compiler and audited as part of the Trust Layer certification process.

The canonicalization rules are monotonic: applying the rules to an already-canonical form produces the same canonical form (idempotency). This property ensures that repeated canonicalization does not alter the representation, which is important for verification processes that re-canonicalize intermediate results to confirm consistency. The idempotency property is verified through a dedicated test suite containing 2,000 canonical forms, each re-canonicalized and compared against itself.

Canonicalization rules are versioned alongside the LDIR rulebook. When the rulebook is updated (adding new resolution rules, modifying default behaviors), the canonicalization rules are updated simultaneously to maintain consistency. The co-versioning strategy prevents the subtle divergence that could occur if the resolution rules and the canonicalization rules evolved independently.

7 Integration with Trust Layer
7.1 Certificate-Bound Intent
Every English Mode compilation produces a certificate chain that binds the English source text to the compiled executable through the Trust Layer Certificate Fabric [3]. The chain consists of three certificates: a SOURCE certificate (binding the English text hash to the compiler's identity), a RESOLUTION certificate (binding the resolution path to the source hash), and a COMPILE_ROOT certificate (binding the AST hash to the resolution result). Together, these certificates provide a complete, cryptographically verifiable record of the compilation process.

The certificate chain enables independent verification of the compilation's correctness. A verifier who receives the compiled executable and the certificate chain can re-compile the English source through the same LDIR tolerance chain and compare the resulting AST hash against the hash recorded in the COMPILE_ROOT certificate. If the hashes match, the compilation is confirmed correct. If they differ, the compilation is suspect and requires investigation. This independent verification does not require trust in the original compiler instance; it requires only trust in the LDIR rulebook version, which is publicly published and independently auditable.

Certificate-bound intent also enables forensic analysis of English Mode programs. When a program produces an unexpected outcome, the forensic analyst can trace the certificate chain backward from the execution outcome through the compilation certificates to the original English source. This trace reveals how the English expression was interpreted, which resolution rules were applied, and which arbitration decisions were made—providing the information needed to determine whether the unexpected outcome resulted from a programming error (incorrect English expression) or a resolution error (incorrect rule application).

7.2 Identity Anchoring
English Mode compilations are anchored to the compiling entity's identity through the Trust Layer certificate chain. The SOURCE certificate includes the compiler's identity certificate, which chains to the ecosystem's root authority. This anchoring establishes provenance: any participant can verify who compiled a specific English expression, when the compilation occurred, and under what governance constraints the compilation was performed.

Identity anchoring enables attribution accountability. When an English Mode program causes harm—deleting critical files, broadcasting sensitive data, exceeding resource limits—the certificate chain identifies the entity that compiled the program. This identification does not require runtime logging or forensic reconstruction; it is intrinsic to the compilation artifact's certificate structure. Attribution is permanent, cryptographically verifiable, and unforgeable.

The identity anchoring mechanism also supports delegation tracking. When a human operator compiles an English expression that is subsequently delegated to an autonomous agent, the delegation extends the certificate chain without breaking the identity linkage to the original human operator. The complete chain—from human expression through compilation through delegation through agent execution—is recorded in the Certificate Fabric, enabling governance authorities to trace any autonomous action back to the human intent that originated it.

7.3 Provenance and Auditability
The English Mode compilation pipeline produces a complete provenance trail that is stored in the Trust Layer Certificate Fabric. The trail includes the original English text (in its canonicalized form), the resolution path (which LDIR layers were activated), the arbitration decisions (if any), the envelope constraints derived, and the final AST hash. This trail is permanent and cryptographically sealed, ensuring that the compilation's history cannot be rewritten or selectively omitted.

Auditability extends to the resolution process itself. Each resolution step is logged with its rule identifier, tier, inputs, and output. This granular logging enables auditors to evaluate not merely what the compiler produced but how it produced it—which rules were applied, in what order, with what inputs, and with what results. This process-level auditability is essential for building regulatory confidence in English Mode as a compilation mechanism for safety-critical systems.

The provenance and auditability mechanisms provide the foundation for the Proof-of-Intent consensus mechanism [11]. When an English Mode program executes, the execution certificate includes the originating Intent Tuple, which includes the original English expression. The PoI mechanism can therefore trace any execution outcome back to the human-language intent that originated it, providing a direct, verifiable link between human expression and computational action.

7.4 Governance Constraints
The Trust Layer imposes governance constraints on English Mode compilations through the same governance policy framework used for structured-syntax compilations. Governance policies may restrict the English vocabulary available for compilation (prohibiting verbs associated with dangerous operations), restrict the parameter values accepted (prohibiting specific file paths or network endpoints), or restrict the envelope parameters derived (capping resource allocation below the context's default maximum).

Governance constraints are evaluated at compile time during the certificate-bound validation stage (§4.6). The compiler loads the applicable governance policies from the Trust Layer and evaluates the compiled action against each policy. Violations are reported as compile-time governance errors with diagnostic messages specifying which policy was violated, which aspect of the compilation triggered the violation, and what alternatives the programmer might consider.

The governance constraint mechanism ensures that English Mode cannot be used to bypass governance policies. A programmer who is prohibited from deleting files through structured Lume syntax is equally prohibited from deleting files through English Mode. The governance policies apply to the canonical actions produced by the compilation pipeline, not to the input modality used to express those actions. This modality-independent governance enforcement is essential for maintaining security in a multi-modal compilation environment.

8 Integration with Lume-V
8.1 Envelope Constraints on Intent
Lume-V [4] provides the envelope enforcement mechanism that constrains English Mode programs within deterministic safety boundaries. When the English Mode pipeline derives envelope constraints from the English expression (§4.3), these constraints are passed to the Lume-V wrapper layer, which configures its enforcement parameters to match. The Lume-V wrapper ensures that the runtime behavior of the English Mode program does not exceed the constraints derived at compile time.

The envelope derivation is conservative by design. When the English expression does not explicitly specify a resource limit, the pipeline assigns the most restrictive applicable default. When the expression is ambiguous about resource requirements, the pipeline selects the interpretation with the smallest envelope footprint (§5.2, safety tiebreaker). This conservatism ensures that English Mode programs operate within tighter bounds than necessary rather than exceeding their authorized limits.

The compile-time envelope derivation provides a preview capability that is unavailable in runtime-only enforcement systems. Before execution, the programmer can inspect the derived envelope constraints and verify that they match the intended resource profile. If the derived constraints are too restrictive (because the English expression was too vague about resource requirements), the programmer can rephrase the expression with explicit resource specifications. This interactive refinement cycle enables the programmer to control the envelope without learning the envelope specification language.

8.2 Safety Boundaries
Safety boundaries for English Mode programs are defined through the same Lume-V behavioral profile mechanism used for non-English Mode programs. The behavioral profile specifies the expected interaction patterns (which modules will be invoked, which data types will be processed, which communication channels will be used) and the Lume-V wrapper monitors the runtime behavior against this profile.

English Mode introduces a unique safety boundary consideration: the behavioral profile is derived from the English expression rather than from explicit specification. The derivation process analyzes the semantic content of the expression to predict the program's behavioral pattern. This prediction is deterministic (the same expression always produces the same prediction) but may be imprecise (the prediction may be broader or narrower than the actual behavior). Imprecision in the broader direction is safe (the profile permits behaviors that the program does not exhibit); imprecision in the narrower direction triggers safe violations (the program attempts a behavior that the profile does not anticipate, causing the Lume-V wrapper to intervene).

The safety boundary mechanism provides defense-in-depth for English Mode compilations. Even if the intent resolution pipeline produces an incorrect compilation—mapping the English expression to a different action than the programmer intended—the Lume-V safety boundaries prevent the incorrect action from exceeding the authorized behavioral envelope. The programmer may observe unexpected behavior within the envelope, but the safety boundaries prevent the unexpected behavior from causing damage beyond the authorized scope.

8.3 Intent Arbitration
Lume-V participates in the compile-time intent arbitration process by providing envelope information that influences the arbitration decision. When the arbitration mechanism evaluates competing interpretations (§5.1), it queries the Lume-V wrapper configuration for the compilation context's envelope constraints. Interpretations that would violate the envelope are eliminated from the candidate set, reducing the ambiguity space and potentially resolving the arbitration without requiring the priority rules.

This Lume-V participation in compile-time arbitration creates a feedback loop between the safety enforcement layer and the compilation layer. The Lume-V envelope constraints, which are typically defined by the deployment environment, influence the compilation output by eliminating interpretations that the deployment environment would not permit. This influence ensures that English Mode compilations are tailored to their deployment context, producing programs that are compatible with the environment's safety constraints by construction rather than by runtime enforcement alone.

The feedback loop is deterministic: the same envelope constraints always eliminate the same interpretations and influence the arbitration in the same way. The Lume-V wrapper configuration is part of the compilation context, and the compilation context is included in the compilation certificate's hash computation. Any change to the Lume-V configuration changes the compilation context, potentially altering the arbitration outcome and producing a different compiled program with a different certificate chain.

8.4 Runtime Enforcement
Lume-V runtime enforcement for English Mode programs is identical to enforcement for structured-syntax programs. The wrapper intercepts all system calls, memory allocations, and network requests, validating each against the envelope constraints. The wrapper emits continuous telemetry to the Homeostasis Engine, enabling proactive intervention when resource consumption approaches envelope boundaries.

The runtime enforcement mechanism is unaware of the English Mode origin of the program it monitors. The wrapper receives a canonical AST and an envelope specification; it does not know or care whether these artifacts were produced from English prose or from structured syntax. This input-modality blindness ensures that English Mode programs receive exactly the same enforcement guarantees as structured-syntax programs—no stronger, no weaker, no different.

Runtime enforcement also provides the data collection infrastructure for English Mode pipeline improvement. The telemetry data collected by the Lume-V wrapper reveals the actual resource consumption and behavioral patterns of English Mode programs. This data can be compared against the compile-time envelope predictions to evaluate the accuracy of the envelope derivation process. Systematic over-estimation (predicted envelopes much larger than actual behavior) suggests that the constraint extraction stage is too conservative; systematic under-estimation (actual behavior approaching envelope limits) suggests that the constraint extraction stage is not conservative enough.

9 Integration with DAIGS
9.1 Cognitive Substrate Extensions
The DAIGS cognitive substrate [5] provides evaluation logic that the English Mode pipeline leverages for compound intent resolution. When an English expression contains multiple actions with complex dependencies ("create a report from the sales data, summarize the key trends, and email the summary to the team if the quarterly target was met"), the cognitive substrate evaluates the inter-action dependencies and produces a deterministic execution ordering.

The cognitive substrate's role in English Mode compilation extends beyond dependency analysis to semantic coherence evaluation. The substrate evaluates whether the aggregate intent of a compound expression is internally consistent: does the sequence of actions form a coherent operational plan, or does it contain contradictions that would prevent successful execution? Detected contradictions are reported as compile-time semantic coherence errors.

The integration between English Mode and the DAIGS cognitive substrate follows the same module interface used for DAIGS multi-agent coordination. The English Mode pipeline submits compound intent evaluation requests to the cognitive substrate and receives deterministic evaluation results. This interface reuse ensures that English Mode leverages the same reasoning capabilities used for autonomous agent coordination, maintaining consistency across the ecosystem's cognitive operations.

9.2 Arbitration Extensions
The DAIGS arbitration engine supports English Mode's compile-time arbitration by providing conflict classification logic for ambiguous English expressions. When the English Mode pipeline detects competing interpretations that the standard priority rules cannot resolve, it escalates the arbitration to the DAIGS engine, which applies the four-category conflict taxonomy (CLASS-A through CLASS-D) to classify the ambiguity and determine the appropriate resolution strategy.

Escalation to the DAIGS arbitration engine is rare: the standard priority rules resolve the vast majority of English Mode ambiguities without escalation. Escalation occurs primarily for expressions involving complex multi-action dependencies where the competing interpretations differ not in the individual actions but in the dependency structure between actions. These structural ambiguities require the cognitive evaluation capabilities that the DAIGS substrate provides.

Escalated arbitration decisions are certified and archived in the Certificate Fabric alongside non-escalated decisions. The Arbitration Certificate for an escalated decision includes the escalation reason, the DAIGS classification, and the resolution strategy applied. This additional documentation enables auditors to distinguish routine arbitration from complex escalated arbitration, providing appropriate scrutiny for the more complex cases.

9.3 Multi-Agent Cognition
English Mode integrates with DAIGS multi-agent cognition to support English Mode programming in multi-agent environments. When multiple autonomous agents independently compile English Mode programs that interact with shared resources, the DAIGS coordination layer ensures that the independently compiled programs operate cohesively within the shared governance framework.

Multi-agent cognition extends English Mode's compile-time analysis to include interaction analysis: the compiler evaluates how the English Mode program will interact with other agents' programs, identifying potential conflicts and coordination requirements. These interactions are analyzed through the DAIGS cognitive substrate and resolved through the GUPAS Arbitration Pipeline, ensuring that English Mode programs from different agents compose coherently within the same ecosystem.

The interaction analysis is conservative: it flags potential interactions for governance review rather than attempting to resolve them automatically. The governance authority reviews the flagged interactions and determines whether they are benign (no action required), coordinated (requiring a session certificate to manage the interaction), or conflicting (requiring arbitration to determine priority). This human-in-the-loop gate ensures that cross-agent English Mode interactions receive appropriate oversight.

9.4 Distributed Reasoning
English Mode compilation in distributed environments leverages the DAIGS distributed cognition model to maintain consistent resolution across geographically distributed compilation nodes. When the same English expression is compiled on different nodes, the LDIR rulebook version, the verb synonym table version, and the action-to-AST table version must be identical across all nodes. The DAIGS certified state delta synchronization mechanism ensures that all compilation nodes maintain identical copies of these configuration artifacts.

Distributed reasoning also supports English Mode compilation for distributed programs—programs whose compiled actions execute across multiple nodes. The DAIGS cognitive substrate evaluates the distribution requirements of the compiled actions and generates the coordination certificates needed to manage cross-node execution. This distribution analysis is performed at compile time, enabling the programmer to understand the distributed behavior of their English Mode program before execution begins.

The distributed compilation model extends transparently to the English Mode pipeline. A programmer writing English Mode on a local node and deploying the compiled program to a remote cluster receives the same deterministic guarantees as a programmer compiling and executing on a single node. The distribution is handled by the infrastructure layers (DAIGS coordination, Trust Layer certification, SOR cell management) without requiring the programmer to modify their English expressions.

10 Integration with LDIR
10.1 Multilingual Normalization
While this paper focuses on English Mode, the LDIR's multilingual architecture ensures that the intent resolution pipeline extends to non-English natural-language modes. The LDIR's language-routing pipeline identifies the source language, applies language-specific grammar rules, and maps the result to the universal intent schema [1]. English Mode is one instantiation of this multilingual capability; Japanese Mode, Spanish Mode, and other language modes follow the same architectural pattern with language-specific normalization rules.

Multilingual normalization for English Mode ensures that English expressions from different English dialects (American English, British English, Australian English) resolve identically. Variant spellings ("color" vs. "colour," "organize" vs. "organise") are mapped to canonical spellings through a dialect normalization table. Variant terminology ("trash" vs. "bin," "elevator" vs. "lift") is mapped to canonical terminology through the same verb synonym table. These normalizations ensure that the resolution outcome is independent of the programmer's English dialect.

The multilingual normalization architecture enables cross-lingual equivalence verification. A programmer who writes an English Mode expression and a Japanese Mode expression that are intended to express the same intent can verify equivalence by comparing the resulting Intent Tuple hashes. If the hashes match, the cross-lingual expressions are equivalent. If they differ, the programmer can examine the resolution paths to identify the semantic divergence.

10.2 Semantic Equivalence
Semantic equivalence for English Mode expressions is defined through the canonical AST hash comparison. Two English expressions are semantically equivalent if and only if they produce identical canonical ASTs when compiled through the English Mode pipeline. This definition is mathematically precise and mechanically computable: compile both expressions, hash both ASTs, compare the hashes.

Semantic equivalence enables deduplication of English Mode programs. When an agent compiles an English expression that is semantically equivalent to a previously compiled expression, the system can reuse the previous compilation's certificate chain and compiled artifact, avoiding redundant compilation. This deduplication is safe because the determinism guarantee ensures that recompilation would produce an identical result.

The semantic equivalence definition also enables regression testing. A corpus of English expression pairs, with verified equivalence or non-equivalence, can be re-evaluated after every pipeline update to detect regressions. A pair that was equivalent before the update but non-equivalent after indicates a regression in the normalization or grounding logic; a pair that was non-equivalent before but equivalent after indicates an unintended conflation of distinct meanings.

10.3 Cross-Lingual Determinism
Cross-lingual determinism requires that the same computational intent expressed in different natural languages produces the same Intent Tuple. For English Mode, this means that an English expression and its translation into any other supported language must resolve to the same canonical action, the same AST, and the same hash. This guarantee is enforced through the universal intent schema, which defines intent representations independent of any specific language.

Cross-lingual determinism is verified through a multilingual test corpus containing expression pairs in all supported language combinations. Each pair consists of two expressions in different languages that are manually certified to express the same computational intent. The test verifies that both expressions resolve to the same Intent Tuple hash. A failure in any pair triggers a review of the language-specific normalization tables to identify and correct the source of the cross-lingual divergence.

The cross-lingual determinism guarantee has practical importance for globally distributed teams. A team in Tokyo and a team in Nashville can independently write English Mode and Japanese Mode programs, respectively, to express the same operational directives. The cross-lingual determinism guarantee ensures that both teams' programs produce identical behavior, enabling distributed collaboration without the risk of interpretation divergence.

10.4 Global Inference
The Evolver's global inference patterns extend to English Mode compilation. As the LDIR processes English Mode expressions across the ecosystem, it tracks which resolution paths are most frequently traversed, which verb mappings are most commonly activated, and which ambiguity patterns are most commonly encountered. These patterns inform the refinement of the English Mode pipeline for subsequent compiler versions.

Global inference operates at the Default tier (Tier 1) of the LDIR hierarchy. English Mode-specific patterns do not receive higher priority than structured-syntax patterns; they compete for influence through the same pattern-weighting mechanism. This parity ensures that the Evolver does not bias the LDIR's resolution behavior toward English Mode at the expense of structured-syntax compilation.

The pattern-capture mechanism also provides usage analytics for the English Mode pipeline. Patterns revealing frequently rejected English expressions (expressions that trigger HALT) inform the development of new resolution rules or the expansion of the verb synonym table. Patterns revealing frequently arbitrated expressions (expressions that trigger compile-time arbitration) inform the development of disambiguation guidelines for English Mode programmers.

11 English Mode Failure Modes
11.1 Ambiguity Collapse
Ambiguity collapse occurs when the LDIR tolerance chain fails to resolve an English expression—all seven layers are exhausted without producing a deterministic resolution. The expression is genuinely ambiguous in a way that no resolution rule can deterministically resolve. The compiler emits a HALT with diagnostic information identifying the unresolvable ambiguity and suggesting alternative phrasings.

Ambiguity collapse is the safest failure mode: the compiler does not guess, does not default, and does not produce an arbitrary resolution. The programmer receives explicit notification that their expression exceeds the compiler's resolution capability and must be rephrased. This explicit failure is preferable to silent misinterpretation, which could produce programs that execute deterministically but do not match the programmer's intent.

The frequency of ambiguity collapse in practice depends on the expressiveness of the LDIR rulebook and the verb synonym table. Empirical analysis of the 10,000-case determinism verification corpus suggests that ambiguity collapse occurs in approximately 2-4% of naturalistic English expressions, with the rate decreasing as the rulebook and synonym table are expanded in subsequent compiler versions.

11.2 Over-Specification
Over-specification occurs when the English expression provides more detail than the compilation pipeline can represent in the canonical AST. The expression "quickly and efficiently create a compressed, encrypted, time-stamped backup of the entire database to the read-heavy NVMe SSD array" contains qualifiers (quickly, efficiently, compressed, encrypted, time-stamped, read-heavy, NVMe SSD) that exceed the canonical action vocabulary's parameter capacity. The pipeline resolves the core action (CREATE backup of database) but must handle the excess qualifiers.

English Mode handles over-specification through modifier prioritization. Qualifiers that map to canonical parameters are incorporated into the Intent Tuple. Qualifiers that do not map to canonical parameters are logged in the compilation metadata as "unresolved modifiers" and reported to the programmer as informational warnings. The programmer can then decide whether the unresolved modifiers are essential (requiring a rephrase or parameter extension) or incidental (safe to ignore).

The over-specification failure mode is benign: the program compiles and executes, but some aspects of the programmer's intent are not captured in the compiled artifact. The informational warnings ensure that the programmer is aware of the gap between their expression and the compilation output, enabling them to take corrective action if needed.

11.3 Under-Specification
Under-specification occurs when the English expression does not provide sufficient information for the compilation pipeline to produce a complete Intent Tuple. The expression "do the thing" does not specify which action, which object, or which parameters. The pipeline cannot resolve the expression because the semantic grounding stage cannot identify a canonical action verb, a canonical object, or any parameter bindings.

English Mode handles under-specification through the LDIR's AI fallback layer (Layer 7 of the tolerance chain). The fallback layer attempts to infer the missing information from the compilation context (the context stack, the active module, the recent compilation history). If the fallback layer succeeds, the inferred information is incorporated into the Intent Tuple with a flagged provenance marker indicating that the information was inferred rather than explicitly stated. If the fallback layer fails, the compiler emits a HALT with a diagnostic message requesting additional specificity.

The provenance marker for inferred information is critical for governance compliance. The GUPAS governance layer can be configured to reject Intent Tuples that contain inferred parameters, requiring the programmer to provide explicit specifications for all sensitive operations. This governance configuration enables organizations to enforce a minimum specificity standard for English Mode programs in safety-critical environments.

11.4 Conflicting Constraints
Conflicting constraints occur when the English expression contains contradictory specifications. The expression "create a read-only file and write today's date to it" contains a contradiction: read-only files cannot be written to. The constraint extraction stage detects the conflict between the "read-only" modifier and the "write" action and reports it as a compile-time constraint conflict error.

Constraint conflict detection operates through a consistency checker that evaluates the extracted constraints against a compatibility matrix. The matrix specifies which parameter values are compatible with which actions. "Read-only" is incompatible with WRITE. "Offline" is incompatible with SEND. "Immutable" is incompatible with UPDATE. The matrix is version-locked to the LDIR rulebook version and is comprehensive across all canonical actions and parameter types.

Conflicting constraints are reported as compile-time errors with diagnostic messages identifying the conflicting elements and suggesting resolutions. The diagnostic system generates multiple alternative phrasings that would resolve the conflict, enabling the programmer to select the phrasing that matches their intended meaning. This guided resolution accelerates the programmer's iterative refinement cycle.

11.5 Semantic Drift
Semantic drift occurs when the meaning of an English word or phrase shifts over time, causing the same expression to resolve differently across compiler versions. The LDIR addresses semantic drift through version-locked vocabulary: the verb synonym table, the parameter mapping table, and the modifier classification table are all frozen at compiler release and do not change between compilations. Semantic drift affects the relationship between natural-language conventions and compiler conventions, not the compiler's behavior itself.

The version-locking strategy means that programmers who upgrade their Lume compiler may find that some English expressions resolve differently in the new version. The compiler provides a migration analysis tool that re-compiles a corpus of English Mode programs under the new version and reports any resolution changes. This tool enables programmers to identify and adapt expressions that were affected by vocabulary updates before deploying the new compiler version to production.

Semantic drift is a managed risk rather than an uncontrolled threat. Each compiler version's vocabulary is published and immutable, enabling programmers to understand the exact meaning of every English word within the compiler's context. The vocabulary is not intended to match contemporary English perfectly; it is intended to provide a stable, deterministic mapping that enables reliable compilation.

11.6 Intent Inversion
Intent inversion occurs when the English Mode pipeline correctly resolves an English expression into a canonical action that is the precise opposite of the programmer's intent. The expression "don't delete the backup files" could be misresolved as DELETE(target="backup files") if the negation handling logic fails to propagate the "don't" modifier to the action verb. Intent inversion is the most dangerous failure mode because the program compiles and executes deterministically—producing a result that is deterministically wrong.

English Mode mitigates intent inversion through a dedicated negation detection and propagation system. The lexical normalization stage identifies negation markers (not, don't, never, no, without, unless) and propagates them through the semantic grounding stage as action modifiers. A negated action verb is mapped to its canonical negation: "don't delete" maps to PRESERVE, "never send" maps to BLOCK_SEND, "no access" maps to DENY_ACCESS. The negation propagation is verified through a dedicated test suite containing 500 negated expression pairs.

The negation detection system also handles double negatives ("don't not delete" maps to DELETE), contextual negation ("delete everything except the backup files" maps to DELETE with an exclusion parameter), and implicit negation ("keep the backup files" implies "don't delete the backup files" through the verb synonym table's mapping of KEEP to PRESERVE). These nuanced negation patterns are tested through the determinism verification corpus and are subject to the same version-locking strategy as all other vocabulary components.

12.6 Deterministic Debugging and Recovery
English Mode programs benefit from the same certificate-based debugging approach available for structured-syntax programs. When an English Mode program produces unexpected behavior, the debugger traces the certificate chain backward from the runtime outcome through the compilation certificates to the original English expression. The resolution path recorded in the RESOLUTION certificate reveals how the English expression was interpreted, enabling the debugger to determine whether the unexpected behavior resulted from a programming error or a resolution anomaly.

Recovery for English Mode programs uses the same Healing Pipeline and Reversal Pipeline as structured-syntax programs. The English Mode origin of the program is irrelevant to the recovery mechanisms; they operate on the canonical AST and the state commitments, which are independent of the input modality. This recovery transparency ensures that English Mode programs receive the same fault tolerance guarantees as structured-syntax programs.

English Mode's natural-language expressiveness provides a unique debugging advantage: the original English expression is often more informative than structured syntax for understanding the programmer's intent. A debugger examining an English Mode program can read the original expression to understand what the programmer was trying to accomplish, rather than reverse-engineering the intent from the compiled code. This semantic transparency accelerates the debugging process.

13 Security Analysis
13.1 Intent Tampering Resistance
Intent tampering in the English Mode context involves modifying the English expression, the resolution path, or the compiled AST after compilation. All three attack vectors are mitigated by the certificate chain binding. The SOURCE certificate binds the English expression's hash to the compiler's identity. The RESOLUTION certificate binds the resolution path to the source hash. The COMPILE_ROOT certificate binds the AST hash to the resolution. Any modification to any component changes the respective hash and invalidates the downstream certificates.

English Mode introduces a unique intent tampering vector: modification of the normalized form. An attacker might attempt to modify the lexically normalized representation between the lexical normalization stage and the semantic grounding stage. This attack is mitigated by the pipeline's internal hash chain: each stage hashes its output and passes the hash to the next stage. The certificate-bound validation stage verifies the complete hash chain, detecting any intermediate modification.

The combination of external certificate binding and internal hash chaining provides defense-in-depth against intent tampering. An attacker must simultaneously modify the English expression, the normalization output, the grounding output, the constraint extraction output, the Intent Tuple, the AST, all associated hashes, and all associated certificates—a combination of modifications that is computationally infeasible.

13.2 Identity Forgery Resistance
Identity forgery for English Mode compilations inherits the Ed25519 security properties of the Trust Layer certificate infrastructure [3]. The SOURCE certificate identifies the compiling entity through its Ed25519 public key, bound to the certificate chain through digital signatures. Forging the compiler's identity requires compromising the compiler's private key or solving the discrete logarithm problem on Curve25519—both computationally infeasible operations.

English Mode does not introduce new identity forgery vectors beyond those present in structured-syntax compilation. The compilation pipeline is the same; the certificate chain is the same; the identity binding is the same. The input modality (English vs. structured syntax) does not affect the cryptographic properties of the identity infrastructure.

The identity anchoring mechanism ensures that every English Mode compilation is attributable to a specific entity. This attribution is permanent, unforgeable, and independently verifiable. Even if the original English expression is no longer available, the SOURCE certificate provides the expression's hash, which can be compared against candidate expressions to identify the original input.

13.3 Certificate Forgery Resistance
Certificate forgery resistance for English Mode certificates inherits the same multi-layered defense as canonical certificate forgery resistance [3]: Ed25519 signature verification, SHA3-256 hash binding, certificate chain validation, append-only archival, and Merkle inclusion proofs. English Mode adds the resolution path attestation to the certificate, providing an additional verification dimension: any forged certificate that claims a resolution path inconsistent with the LDIR rulebook is detectable through re-resolution.

The re-resolution verification is a powerful forgery detection mechanism. Given the English expression and the LDIR rulebook version, any participant can independently re-resolve the expression and compare the result against the claimed resolution. A forged certificate that claims a different resolution path will fail this re-verification, even if Ressl its signatures and hashes are mathematically valid. This semantic verification complements the cryptographic verification, providing defense beyond what purely mathematical mechanisms can achieve.

The combination of cryptographic and semantic verification makes English Mode certificate forgery more difficult than canonical certificate forgery, because the attacker must forge certificates that are both cryptographically valid and semantically consistent with the deterministic resolution process.

13.4 Replay Attack Mitigation
Replay attacks against English Mode compilations are mitigated through the same nonce-and-monotonic-timestamp mechanism used for all Lume compilations. Each compilation includes a unique nonce derived from the compiler's state hash and the compilation timestamp. Replaying a previously captured compilation produces a nonce that does not match the compiler's current state, causing rejection.

English Mode introduces a subtle replay consideration: the same English expression, compiled at different times, should produce the same compiled artifact (determinism) but should generate different certificates (replay resistance). The English Mode pipeline achieves this by including the compilation timestamp and nonce in the certificate but not in the AST hash. The AST is deterministic (same expression → same AST); the certificate is unique (different timestamp → different certificate). This separation ensures that determinism and replay resistance coexist without contradiction.

The replay mitigation mechanism also prevents attackers from pre-computing English Mode compilations for future replay. An attacker who compiles a malicious English expression today cannot replay the resulting certificate tomorrow, because the nonce will not match the ecosystem's state at replay time.

13.5 Governance Abuse Prevention
Governance abuse prevention for English Mode follows the same multi-signature and transparency mechanisms used for canonical governance. Critical governance operations (modifying the verb synonym table, updating the LDIR rulebook, changing the arbitration priority rules) require co-signatures from the governance quorum. All governance actions are published to the Certificate Fabric and visible to all ecosystem participants.

English Mode introduces a governance abuse vector specific to natural-language compilation: vocabulary manipulation. An attacker with governance authority might modify the verb synonym table to remap a benign verb to a dangerous canonical action—for example, remapping "save" from WRITE_FILE to DELETE_FILE. This attack is mitigated by the multi-signature requirement for vocabulary updates and by the determinism verification corpus, which would detect the remapping through test case failures.

The Evolver's pattern-capture mechanism extends to English Mode governance, tracking the frequency and scope of vocabulary updates and resolution rule changes. Unusual patterns (frequent vocabulary changes, large-scope rule modifications, changes that affect high-frequency expressions) generate governance alerts that are distributed to all governance authorities, enabling collective oversight of English Mode governance actions.

14 Performance Considerations
14.1 Intent Resolution Overhead
The English Mode intent resolution pipeline introduces overhead relative to structured-syntax compilation. The lexical normalization stage adds approximately 0.5 milliseconds per 100 tokens. The semantic grounding stage adds approximately 1.0 millisecond per canonical action identified. The constraint extraction stage adds approximately 0.3 milliseconds per constraint derived. The intent tuple formation, AST mapping, and certificate-bound validation stages add approximately 0.8 milliseconds combined. The aggregate pipeline overhead for a typical English Mode expression (20-50 tokens, 1-3 actions) is approximately 3-5 milliseconds.

This overhead is negligible for interactive programming sessions, where the programmer's typing latency dwarfs the compilation latency. For batch compilation of large English Mode corpora, the overhead may become significant; the pipeline supports parallel compilation of independent expressions to mitigate batch overhead. The parallelization follows the same deterministic scheduling used for structured-syntax parallel compilation, ensuring that the compilation order does not affect the output.

The overhead is offset by the elimination of the programmer's mental translation step. In structured-syntax programming, the programmer mentally translates their English intent into Lume syntax; in English Mode, this translation is performed by the compiler. The time savings from eliminating the mental translation step typically exceed the pipeline's computational overhead, resulting in a net productivity improvement for most programming tasks.

14.2 Arbitration Latency
Compile-time intent arbitration adds latency when ambiguous English expressions trigger the arbitration mechanism. The standard priority rule evaluation adds approximately 0.1 milliseconds per competing interpretation. The envelope constraint filtering adds approximately 0.05 milliseconds per interpretation evaluated. For typical ambiguity levels (2-3 competing interpretations), the total arbitration latency is approximately 0.3-0.5 milliseconds—imperceptible in interactive sessions.

Escalation to the DAIGS arbitration engine adds approximately 2-5 milliseconds per escalated arbitration. Escalation is rare (estimated at less than 0.5% of English Mode compilations), so the aggregate impact on average compilation latency is negligible. For expressions that frequently trigger escalation, the programmer can reduce arbitration latency by rephrasing the expression to reduce ambiguity.

The arbitration latency is bounded: the LDIR cascade has a fixed number of tiers and a fixed number of rules per tier, and the priority rule evaluation terminates at the first successful resolution. The worst-case arbitration latency is therefore proportional to the total number of rules in the LDIR cascade, which is known at compiler initialization and does not grow during compilation.

14.3 Distributed Cognition Cost
Distributed English Mode compilation introduces network latency when the DAIGS cognitive substrate is distributed across multiple nodes. The cognitive evaluation requests generated by the English Mode pipeline (compound intent analysis, semantic coherence checking, dependency ordering) are routed to the appropriate cognitive node through the DAIGS cognitive routing protocol. The network round-trip latency adds approximately 1-10 milliseconds per cognitive evaluation, depending on the geographic distance between the compilation node and the cognitive node.

The distributed cognition cost is mitigated through cognitive caching: the compilation node maintains a local cache of recent cognitive evaluation results, avoiding redundant remote evaluations for expressions similar to previously evaluated expressions. The cache hit rate depends on the diversity of expressions compiled on the node; for typical programming sessions with repetitive expression patterns, the cache hit rate exceeds 80%, reducing the average distributed cognition cost to approximately 0.2-2.0 milliseconds per compilation.

The distributed cognition model is transparent to the programmer. English Mode expressions are compiled with the same syntax, the same resolution rules, and the same deterministic guarantees regardless of whether the cognitive substrate is local or distributed. The distribution is an infrastructure concern managed by the DAIGS configuration, not a programming concern that the programmer must address.

15 Future Work
15.1 Cross-Vertical Intent Resolution
Future work will extend English Mode's intent resolution to accommodate cross-vertical expressions that span multiple DAIGS domain verticals. The expression "process the patient's insurance claim and notify the billing department" spans the medical vertical (patient) and the financial vertical (insurance claim, billing). Current English Mode resolution handles each vertical independently; future work will develop cross-vertical resolution rules that coordinate the domain-specific grounding across verticals.

Cross-vertical intent resolution requires the verb synonym table and the parameter mapping table to support multi-vertical contexts. A term like "claim" may have different canonical meanings in the medical vertical (insurance claim) and the legal vertical (legal claim). The cross-vertical resolution must use contextual signals (co-occurring terms, prior expressions, active module) to disambiguate domain-specific terminology within a deterministic framework.

The long-term vision is a unified cross-vertical English Mode that enables programmers to express multi-domain intents in a single English expression, with the compilation pipeline resolving each domain-specific term through the appropriate vertical's resolution rules. This unified mode will operate through the Cross-Vertical Expansion Subsystem described in the doctrine expansion architecture [10].

15.2 ZK-Native Intent Verification
Future work will integrate zero-knowledge proof systems into the English Mode compilation pipeline, enabling the compiler to prove that an English expression was correctly resolved without revealing the expression itself. This privacy-preserving compilation is valuable for organizations that need to demonstrate governance compliance (proving that their English Mode programs comply with policy constraints) without disclosing their proprietary English Mode source code.

ZK-native intent verification requires the development of proof circuits for each stage of the intent resolution pipeline. The lexical normalization circuit must prove correct normalization without revealing the input tokens. The semantic grounding circuit must prove correct verb and object identification without revealing the identified actions. The constraint extraction circuit must prove correct constraint derivation without revealing the derived constraints. Designing these circuits while maintaining acceptable proof generation latency is a significant technical challenge.

The successful implementation of ZK-native intent verification will enable confidential English Mode compilation: a programmer can compile an English expression, produce a compiled artifact with a zero-knowledge certificate, and share the artifact with collaborators who can verify the compilation's correctness without learning the original English expression. This capability has applications in classified computing, trade secret protection, and privacy-sensitive programming domains.

15.3 Autonomous Organism Intent Generation
Future work will enable synthetic organisms to generate English Mode expressions autonomously and compile them through the deterministic pipeline. Currently, English Mode accepts expressions from human programmers; autonomous organisms formulate intents through structured data objects. Enabling organisms to express intents in English Mode would provide the cognitive transparency benefit (human-readable intent formulation) to autonomous organism governance.

Autonomous English Mode generation introduces quality assurance challenges. An organism's English expression may be syntactically valid but semantically imprecise, leading to frequent ambiguity collapses or over-specification warnings. Future work will develop an English Mode expression quality evaluator that assesses an organism's English output before compilation, providing feedback that the organism can use to refine its expression quality through the Evolver's pattern-capture mechanism.

The successful integration of autonomous organism English Mode generation will create a complete natural-language programming loop: humans express intent in English, organisms interpret and execute those intents, organisms generate their own intents in English, and those intents are compiled through the same deterministic pipeline that compiled the human intents. This closed loop, to my knowledge, would represent the first instance of a natural-language programming system that spans both human and autonomous expression within a unified deterministic framework.

15.4 Global Doctrinal Frameworks
Future work will address the challenges of English Mode deployment across jurisdictions with different regulatory requirements. Different jurisdictions may impose different constraints on natural-language compilation (requiring explicit consent for AI-assisted compilation, prohibiting certain vocabulary in regulated domains, mandating specific audit trail formats). Future development will introduce jurisdictional policy layering for English Mode governance.

Global doctrinal frameworks also require standardization of English Mode's cross-lingual capabilities. As English Mode expands to additional languages, the governance framework must ensure consistent treatment across all language modes. Future work will develop international English Mode standards that specify minimum resolution quality, minimum determinism verification corpus size, and minimum cross-lingual equivalence coverage for each supported language.

The long-term objective is an internationally recognized English Mode standard that enables regulatory authorities in any jurisdiction to evaluate and certify English Mode compilations against a common set of quality, safety, and governance criteria. This standardization will facilitate the adoption of English Mode in regulated industries where regulatory approval is a prerequisite for deployment.

16 Conclusion
The gap between human natural-language expression and deterministic computational execution has persisted since the earliest days of programming. Every prior attempt to bridge this gap has relied on probabilistic interpretation—accepting the irreducible variance that statistical inference introduces—or has constrained the input language to a formalized subset that sacrifices the naturalness of the programmer's expression. English Mode demonstrates that neither compromise is necessary. A deterministic compile-time resolution pipeline can transform unconstrained English prose into bit-identical canonical ASTs, providing the safety, reproducibility, and certificate-anchored provenance that the Lume ecosystem requires without constraining the programmer's expressive freedom.

The six-stage intent resolution pipeline—lexical normalization, semantic grounding, constraint extraction, intent tuple formation, canonical AST mapping, and certificate-bound validation—provides a complete, end-to-end path from English expression to certified executable. Each stage is deterministic, producing identical outputs for identical inputs through fixed rule cascades rather than statistical inference. The compile-time intent arbitration mechanism resolves ambiguity through priority rules, envelope constraints, and safety preferences, ensuring that every English expression receives a deterministic interpretation before any runtime execution begins.

The formalization of six failure modes—ambiguity collapse, over-specification, under-specification, conflicting constraints, semantic drift, and intent inversion—provides the diagnostic framework that English Mode compilers need to guide programmers toward successful compilation. These failure modes are detected at compile time, reported with diagnostic messages and suggested alternatives, and resolved through the programmer's iterative refinement. The compile-time detection of all failure modes eliminates the category of "silent misinterpretation" that plagues runtime natural-language interpretation systems.

The integration architecture binds English Mode to every layer of the Lume ecosystem: the Lume compiler (AST format identity), the Trust Layer (certificate-bound provenance), Lume-V (envelope enforcement), DAIGS (cognitive substrate), LDIR (inference rulebook), and GUPAS (governance framework). This integration ensures that English Mode programs are first-class citizens within the governed ecosystem, receiving the same deterministic guarantees, the same security protections, and the same governance oversight as structured-syntax programs.

To my knowledge, this paper presents the first complete compile-time intent resolution pipeline for natural-language programming that provides bit-identical deterministic output with cryptographic provenance guarantees. The pipeline establishes that natural-language programming and deterministic compilation are compatible—that the barrier between human expression and machine certainty can be crossed without sacrificing either the naturalness of the expression or the determinism of the computation. As the Lume ecosystem extends through the Expansion Research Community, English Mode will serve as the primary interface through which human operators interact with deterministic autonomous systems, making the power of deterministic computation accessible through the language that humans already speak.

Appendix A — Definitions
A.1 English Mode
The alternative input frontend of the Lume compiler that accepts unconstrained English prose and transforms it into canonical Abstract Syntax Trees through a deterministic six-stage intent resolution pipeline. English Mode is not a separate compiler; it is an input modality that produces the same internal representations as Lume's structured syntax frontend. English Mode programs execute within the same runtime, receive the same certification, and are governed by the same governance framework as structured-syntax programs.

A.2 Intent Tuple
A formal data structure consisting of five fields: intent source (the original English expression), intent hash (SHA3-256 digest of the canonicalized source), resolved action (the deterministic interpretation produced by the LDIR tolerance chain), trust binding (the certificate anchoring the intent to the compiler's identity), and envelope constraint (the safety boundary derived from the expression's semantic content). The Intent Tuple propagates through every Lume ecosystem layer from compilation through certification.

A.3 Semantic Normalization
The process of transforming diverse English expressions that convey the same computational intent into a single canonical form. Semantic normalization operates in three phases: verb normalization (mapping English verbs to canonical action verbs through a synonym table), parameter normalization (mapping English phrases to canonical parameter structures), and structural normalization (decomposing compound sentences into sequences of atomic canonical operations).

A.4 Canonical AST
The deterministic Abstract Syntax Tree produced by the Lume compiler, following a strict construction order (depth-first, left-to-right, canonical reading order). The AST uses a fixed node vocabulary (Program, Command, Sequence, Condition, Block, List, Value, Identifier, ModuleCall, Parameter, Comparison, LogicalExpression, TemporalExpression) and is hashable through SHA3-256 for certificate binding and equivalence checking.

A.5 Envelope Constraint
A declarative policy bounding execution along four dimensions: resource consumption, state mutation scope, external interaction boundaries, and temporal limits. In English Mode, envelope constraints are derived from the English expression's semantic content through the constraint extraction stage and are composed with the execution context's envelope through set intersection (the more restrictive constraint applies).

A.6 Certificate Fabric
The directed acyclic graph of cryptographically signed trust assertions maintained by the Trust Layer. English Mode compilations contribute three certificates to the fabric: SOURCE (binding the English text hash to the compiler identity), RESOLUTION (binding the resolution path to the source hash), and COMPILE_ROOT (binding the AST hash to the resolution result). The fabric is append-only, publicly verifiable, and Merkle-indexed.

A.7 Deterministic Transition Graph
A directed graph representing a program's state evolution, where each node is a committed state (SHA3-256 hash) and each edge is a state transition (intent-triggered). For English Mode programs, the transition graph's edges reference the original English expressions through the Intent Tuple's source field, enabling forensic reconstruction of the program's behavior in natural language.

A.8 Arbitration Layer
The compile-time mechanism within the English Mode pipeline that resolves competing interpretations of ambiguous English expressions. The Arbitration Layer evaluates competing interpretations against priority rules (specificity, precedence, context, safety), envelope constraints (eliminating interpretations that violate the execution context's safety boundaries), and produces a deterministic finalization that selects exactly one interpretation for compilation.

Appendix B — Algorithms
B.1 Intent Resolution Algorithm
Algorithm EnglishModeIntentResolution:
Input: RawEnglishText, CompilerCertificate, ExecutionContext
Output: IntentTuple, CanonicalAST, CertificateChain

 1: NORMALIZE RawEnglishText:
 2:    Whitespace normalization (collapse multiple spaces)
 3:    Case folding (to lowercase for matching)
 4:    Punctuation standardization (typographic → ASCII)
 5:    Encoding normalization (to UTF-8 NFC)
 6:    Contraction expansion (don't → do not)
 7:    Abbreviation resolution (DB → database)
 8: COMPUTE source_hash = SHA3-256(normalized_text)
 9: EMIT SOURCE certificate (source_hash, CompilerCertificate)
10: GROUND semantically:
11:    IDENTIFY action verbs via verb synonym table
12:    IDENTIFY objects via object keyword table
13:    IDENTIFY modifiers via modifier classification table
14:    MAP identified elements to canonical action structures
15: EXTRACT constraints:
16:    DERIVE resource constraints from action profiles
17:    DERIVE scope constraints from state mutation specs
18:    DERIVE interaction constraints from action targets
19:    DERIVE temporal constraints from expression or defaults
20: FORM IntentTuple(source, source_hash, resolved_action, cert, envelope)
21: VALIDATE internal consistency of IntentTuple
22: MAP resolved_action to CanonicalAST via action-to-AST table
23: COMPUTE ast_hash = SHA3-256(canonical AST serialization)
24: EMIT RESOLUTION certificate (resolution_path, source_hash)
25: EMIT COMPILE_ROOT certificate (ast_hash, resolution_hash)
26: VERIFY determinism: re-normalize, compare hashes
27: RETURN (IntentTuple, CanonicalAST, CertificateChain)
B.2 Semantic Normalization Algorithm
Algorithm SemanticNormalization:
Input: NormalizedTokenStream, VerbSynonymTable, ObjectKeywordTable
Output: CanonicalActionSequence

 1: INITIALIZE action_sequence = []
 2: SCAN token_stream for verb tokens:
 3:    FOR each verb_token:
 4:       LOOKUP verb_token in VerbSynonymTable
 5:       IF exact match: canonical_verb = table[verb_token]
 6:       ELIF fuzzy match (edit distance ≤ 2): canonical_verb = closest_match
 7:       ELSE: ESCALATE to AI fallback (Layer 7)
 8: SCAN token_stream for object tokens following each verb:
 9:    FOR each verb-object pair:
10:       LOOKUP object_token in ObjectKeywordTable
11:       IF recognized: canonical_object = table[object_token]
12:       ELSE: canonical_object = VARIABLE(name=object_token)
13: SCAN for modifiers (adverbs, prepositional phrases):
14:    MAP modifiers to canonical parameters
15: DETECT sentence boundaries (conjunctions, semicolons, periods)
16: FOR each sentence boundary:
17:    SPLIT compound expressions into atomic actions
18: ORDER atomic actions by temporal dependencies (LDIR Layer 5)
19: CONSTRUCT CanonicalActionSequence from ordered actions
20: RETURN CanonicalActionSequence
B.3 Constraint Extraction Algorithm
Algorithm ConstraintExtraction:
Input: CanonicalActionSequence, ExecutionContext
Output: EnvelopeConstraints

 1: INITIALIZE constraints = ExecutionContext.default_envelope
 2: FOR each action in CanonicalActionSequence:
 3:    LOAD action.resource_profile from action catalog
 4:    ACCUMULATE resource requirements:
 5:       constraints.cpu += action.resource_profile.cpu_estimate
 6:       constraints.mem += action.resource_profile.mem_estimate
 7:       constraints.net += action.resource_profile.net_estimate
 8:    IDENTIFY state mutation scope:
 9:       constraints.mutable_regions ∪= action.state_mutation_spec
10:    IDENTIFY external interactions:
11:       constraints.endpoints ∪= action.external_targets
12:    IDENTIFY temporal constraints:
13:       IF action has explicit temporal bound: constraints.duration = min(constraints.duration, bound)
14: INTERSECT derived constraints with ExecutionContext.envelope:
15:    final.cpu = min(derived.cpu, context.max_cpu)
16:    final.mem = min(derived.mem, context.max_mem)
17:    final.mutable = derived.mutable ∩ context.mutable
18:    final.endpoints = derived.endpoints ∩ context.endpoints
19:    final.duration = min(derived.duration, context.max_duration)
20: VALIDATE: IF derived exceeds context on any dimension: EMIT WARNING
21: RETURN final EnvelopeConstraints
B.4 Arbitration Algorithm
Algorithm CompileTimeArbitration:
Input: CompetingInterpretations[], EnvelopeConstraints, ContextStack
Output: SelectedInterpretation, ArbitrationCertificate

 1: FILTER: Remove interpretations that violate EnvelopeConstraints
 2: IF single interpretation remains: SELECT it, SKIP arbitration
 3: EVALUATE specificity for each remaining interpretation:
 4:    Score = (exact_match_count × 3) + (parameter_count × 2) + (modifier_count × 1)
 5: IF unique highest score: SELECT highest, CERTIFY, RETURN
 6: EVALUATE precedence for tied interpretations:
 7:    Order by LDIR rule ordinal (lower ordinal = higher precedence)
 8: IF unique highest precedence: SELECT highest, CERTIFY, RETURN
 9: EVALUATE context consistency:
10:    Score each interpretation by context stack match count
11: IF unique highest context match: SELECT highest, CERTIFY, RETURN
12: APPLY safety tiebreaker:
13:    SELECT interpretation with smallest envelope footprint
14: CONSTRUCT ArbitrationCertificate:
15:    Record competing interpretations, scores, rules applied, selected
16: SIGN certificate with compiler Ed25519 key
17: RETURN (SelectedInterpretation, ArbitrationCertificate)

(Illustrative) A decision tree diagram with the root node labeled "Ambiguous Expression Detected." Appendix D — Implementation Notes
D.1 Grammar Primitives
English Mode's grammar primitives are derived from the Lume structured syntax grammar and expressed as natural-language matching patterns. The primitive vocabulary includes 47 canonical action verbs, 23 canonical object types, 15 canonical modifier categories, and 8 canonical structural patterns (sequence, condition, loop, block, module call, expression, temporal, logical). Each primitive is documented with its canonical form, its English synonyms, its parameter schema, and its AST mapping. The primitive vocabulary is published as a machine-readable specification alongside each compiler release.

D.2 Deterministic Parsing Rules
English Mode's parsing rules are implemented as deterministic finite automata (DFAs) that process the normalized token stream. Each DFA recognizes a specific syntactic pattern (verb-object, subject-verb-object, conditional, temporal sequence) and produces a structured parse result. The DFAs are version-locked to the compiler version and loaded as read-only data structures at initialization. Parsing follows priority ordering: more specific DFAs are tried before more general DFAs, ensuring that specific patterns take precedence over generic patterns.

D.3 Integration with Lume Runtime
English Mode integrates with the Lume runtime through the same API surface used by structured-syntax compilation: compile(source) -> AST, execute(AST, cell) -> state_delta. The runtime does not distinguish between ASTs produced from English Mode and ASTs produced from structured syntax. This indistinguishability is verified through the cross-compilation comparison test suite, which compiles 3,000 expression pairs (English + structured syntax) and verifies AST hash identity.

D.4 Trust Layer Hooks
English Mode invokes Trust Layer hooks at three points during compilation: issue_source_cert(source_hash, compiler_id) after lexical normalization, issue_resolution_cert(resolution_path, source_hash) after semantic grounding, and issue_compile_cert(ast_hash, resolution_hash) after AST mapping. These hooks follow the sub-millisecond latency requirements established for canonical Trust Layer operations. The Certificate Fabric indexes English Mode certificates by source hash, enabling efficient retrieval for forensic analysis and deduplication.

D.5 Lume-V Wrapper Requirements
Lume-V wrappers for English Mode programs implement the standard envelope enforcement interface. The wrapper receives the envelope constraints derived by the constraint extraction stage and configures its enforcement parameters accordingly. The wrapper does not perform additional natural-language analysis; it operates on the canonical AST and the derived envelope, which are identical in format to structured-syntax compilation outputs. The wrapper's behavioral profile is derived from the English Mode expression's semantic analysis and is encoded in the compilation certificate.

Appendix E — Governance & Compliance
E.1 Who Can Declare Intent
English Mode intent declaration is restricted to entities possessing valid identity certificates with the INTENT_DECLARE capability, following the same authorization model used for structured-syntax compilation. Human operators receive this capability through their operator certificate. Autonomous agents may declare English Mode intents if they possess the INTENT_GENERATE capability (Type-3+ organisms only). The English Mode frontend does not introduce any additional capability requirements; the authorization model is input-modality-independent.

Organizations can configure additional English Mode-specific authorization requirements through Governance Expansion Subsystem policies [10]. For example, an organization might require that all English Mode compilations in the medical vertical be reviewed by a qualified medical officer before execution. These organization-specific requirements are encoded as governance policies and enforced during the certificate-bound validation stage.

E.2 How Intent Is Governed
English Mode intents are governed through the same GUPAS governance framework used for structured-syntax intents [2]. The governance layer evaluates the compiled action against policy constraints, envelope constraints, and arbitration rules. The evaluation occurs at compile time during the certificate-bound validation stage. Governance violations are reported as compile-time errors, preventing execution before any harm can occur.

English Mode governance includes vocabulary-specific policies. Organizations can restrict the English vocabulary available for compilation, prohibiting verbs associated with dangerous or unauthorized operations. These vocabulary restrictions are enforced during the semantic grounding stage, which checks each identified canonical action against the applicable vocabulary policy. Restricated canonical actions are filtered before the constraint extraction stage, ensuring that prohibited operations cannot reach the compilation output.

E.3 Safety Rules
English Mode safety rules extend the LDIR Tier 4 safety rules with English-specific constraints: EM-01 (Negation Must Be Resolved Before Compilation—every negation marker must be propagated to the corresponding action verb), EM-02 (Ambiguity Must Be Resolved at Compile Time—no unresolved ambiguity may reach the runtime), EM-03 (Envelope Derivation Must Be Conservative—when in doubt, restrict), EM-04 (Certificate Chain Must Be Complete—all three certificates must be successfully emitted), and EM-05 (Determinism Verification Must Pass—final hash comparison must confirm deterministic compilation).

These safety rules are hard-coded into the English Mode pipeline and cannot be modified through governance policies. When an English Mode safety rule activates, the compilation halts and the programmer receives a diagnostic message identifying the safety violation and suggesting corrective rephrasing.

E.4 Interaction with Proof-of-Intent
English Mode provides the strongest Proof-of-Intent signal in the Lume ecosystem [11]. The Intent Tuple produced by English Mode compilation contains the original English expression in the intent source field, providing a human-readable record of the programmer's intent. The PoI mechanism can therefore verify not merely that an execution was preceded by a declared intent but that the declared intent was expressed in human-understandable language and compiled through a deterministic, auditable pipeline.

This natural-language Proof-of-Intent is valuable for regulatory compliance. When a regulator asks "why did this system take this action?", the answer can be traced back to a specific English expression written by a specific person, compiled through a documented resolution path, producing a specific executable action. This end-to-end traceability from human expression to computational action satisfies the governance transparency standards required by financial, medical, and defense regulations.

Appendix F — Extended Examples
F.1 Example English Mode Compilation
A programmer activates English Mode and writes: "Read the customer records from the sales database and create a summary report showing total revenue by region." The lexical normalization stage produces a normalized token stream with contractions expanded and punctuation standardized. The semantic grounding stage identifies two canonical actions: READ(source="sales database", filter="customer records") and CREATE(type="report", template="summary", grouping="region", metric="revenue"). The constraint extraction stage derives the envelope: database read access required, file write access required, no network access, no state mutation beyond the output file.

The intent tuple formation stage assembles the five-field Intent Tuple. The canonical AST mapping stage produces a Sequence node containing two Command children: a ModuleCall to the database module (READ operation) and a ModuleCall to the report module (CREATE operation), with a data dependency from the READ output to the CREATE input. The certificate-bound validation stage emits three certificates and validates the action against governance policies. The compilation succeeds, producing a certified executable with a complete provenance trail from English prose to canonical AST.

F.2 Example Arbitration Scenario
A programmer writes: "Set the connection to secure mode." The semantic grounding stage identifies two competing interpretations: SET(target="connection", parameter="mode", value="secure") and ACTIVATE(target="secure mode", context="connection"). The first interpretation treats "set" as an assignment verb and "secure mode" as a value. The second interpretation treats "set" as an activation verb and "secure mode" as a mode identifier. The compile-time arbitration mechanism activates.

The envelope constraint filter does not eliminate either interpretation (both are within the execution context's envelope). The specificity evaluation scores the first interpretation higher (3 matched parameters vs. 2). The arbitration selects the first interpretation: SET(target="connection", parameter="mode", value="secure"). The Arbitration Certificate records both competing interpretations, the specificity scores, and the selected interpretation. The programmer can review the certificate to verify the compiler's decision.

F.3 Example Certificate-Bound Intent
An autonomous financial monitoring agent compiles an English Mode expression: "Flag all transactions exceeding $10,000 for compliance review." The compilation produces three certificates. The SOURCE certificate records the expression hash (SHA3-256 of the normalized text) and the agent's identity certificate. The RESOLUTION certificate records the resolution path: Layer 1 (exact match for "flag"), Layer 5 (temporal sequencing for the implied scan operation), and the derived action FILTER(source="transactions", condition="amount > 10000", action="FLAG", destination="compliance review queue").

The COMPILE_ROOT certificate records the AST hash and the output hash. The complete certificate chain enables any governance auditor to verify that the agent's compliance flagging behavior originated from a specific English expression, was resolved through specific LDIR rules, and produced a specific executable action. This traceability satisfies the audit requirements of financial regulatory frameworks.

Appendix G — Threat Models
G.1 Malicious Intent Injection
An attacker attempts to inject a malicious English expression into the English Mode pipeline by compromising the input channel between the programmer and the compiler. The attack might involve intercepting the programmer's English text and substituting a malicious expression that compiles to a harmful action. This attack is mitigated by the SOURCE certificate, which binds the expression's hash to the compiler's identity at the moment of compilation. Any substitution changes the hash and is detectable by comparing the SOURCE certificate's hash against the programmer's original expression.

A more sophisticated attack involves crafting English expressions that appear benign to human reviewers but resolve to harmful actions through the LDIR rule cascade. This attack is mitigated by the deterministic resolution transparency: any reviewer who queries the LDIR rulebook can predict how a given expression will be resolved, detecting the mapping to a harmful action before compilation. The resolution path is also recorded in the RESOLUTION certificate, enabling post-hoc detection of suspiciously mapped expressions.

A third attack vector involves modifying the verb synonym table to remap benign verbs to harmful actions. This attack is mitigated by the governance quorum requirement for vocabulary updates and by the determinism verification corpus, which would detect the remapping through test case failures.

G.2 Semantic Manipulation
Semantic manipulation attacks exploit the gap between the programmer's intended meaning and the compiler's deterministic resolution. An attacker crafts English expressions that exploit edge cases in the LDIR rule cascade to produce unexpected resolutions. For example, the expression "secure the data by removing protections" could be interpreted as a security action (secure = protect) or a destructive action (remove protections = delete security).

This attack is mitigated by the negation detection system and the conflicting constraint detector. The expression "removing protections" triggers the negation detection for "removing" (which maps to DELETE), and the constraint detector identifies the conflict between "secure" (a protective action) and "removing protections" (a destructive action). The compile-time error report alerts the programmer to the semantic inconsistency.

Semantic manipulation that evades the constraint detector is mitigated by the Arbitration Certificate's transparency. The certificate records which interpretation was selected and why, enabling post-compilation review that can detect suspicious arbitration outcomes. Organizations that operate in high-security environments can require mandatory Arbitration Certificate review for all English Mode compilations.

G.3 Governance Manipulation
Governance manipulation involves using governance authority to alter the English Mode pipeline's behavior for unauthorized purposes. An attacker with governance authority might modify the LDIR rulebook to introduce resolution rules that favor the attacker's intents, or might alter the verb synonym table to remap verbs in ways that bypass governance restrictions.

This attack is mitigated by the multi-signature requirement for LDIR rulebook updates and vocabulary modifications. No single governance authority can unilaterally modify the pipeline's behavior. The determinism verification corpus provides an independent check: any modification that changes the resolution behavior for test corpus expressions is detected before the modification takes effect.

Long-term governance manipulation—gradually introducing small changes that cumulatively alter the pipeline's behavior—is detected by the Evolver's pattern-capture mechanism, which tracks cumulative changes to the LDIR rulebook and verb synonym table and generates alerts when cumulative modification exceeds statistical thresholds.

Appendix H — Formal Notation
H.1 Intent Tuple Notation
An Intent Tuple is formally represented as a quintuple I = (s, h, a, c, e) where s ∈ Σ* is the intent source (a string over the alphabet Σ), h = SHA3-256(κ(s)) is the intent hash (where κ is the canonicalization function), a = LDIR(κ(s)) is the resolved action (the output of the LDIR tolerance chain applied to the canonicalized source), c ∈ 𝓞 is the trust binding (a certificate from the certificate space 𝓞), and e = (R, M, X, T) is the envelope constraint (the resource-scope-interaction-temporal quadruple). The determinism invariant requires: ∀ s1, s2 ∈ Σ*: κ(s1) = κ(s2) ⇒ I(s1) = I(s2).

H.2 Semantic Equations
The semantic normalization function N: T* → A* maps a token stream T* = (t1, t2, ..., tn) to a canonical action sequence A* = (a1, a2, ..., am) through the composition of three sub-functions: N = σ ∘ π ∘ ν, where ν: T* → V* is verb normalization (mapping tokens to canonical verbs), π: V* → P* is parameter normalization (mapping verb contexts to parameter bindings), and σ: P* → A* is structural normalization (decomposing compound expressions into atomic actions). Each sub-function is deterministic: ∀ x: f(x) = f(x) (trivially, but verified through the determinism test corpus). The composition is therefore deterministic: N(T) = σ(π(ν(T))) is a deterministic function from token streams to action sequences.

H.3 Envelope Rules
The envelope derivation function E: A* × C → 𝔼 maps a canonical action sequence A* and an execution context C to an envelope 𝔼 = (R, M, X, T). The derivation follows the accumulation rule: R = Σi R(ai), M = ∪i M(ai), X = ∪i X(ai), T = maxi T(ai). The context intersection rule: 𝔼' = 𝔼 ∩ C.envelope = (min(R, C.R), M ∩ C.M, X ∩ C.X, min(T, C.T)). The intersection guarantees 𝔼' ⊆ 𝔼 and 𝔼' ⊆ C.envelope, ensuring that the derived envelope is simultaneously within the expression's requirements and within the context's authorization.
