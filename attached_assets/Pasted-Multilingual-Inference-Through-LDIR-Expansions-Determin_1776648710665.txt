Abstract
The Lume Deterministic Inference Relay (LDIR) provides the multilingual substrate through which the Lume programming language resolves natural-language expressions into deterministic computational intent. The canonical LDIR specification defines 31 inference rules across 4 tiers, governing how English-language expressions traverse the seven-layer tolerance chain to produce canonical Intent Tuples. As the Lume ecosystem extends to serve globally distributed teams, autonomous agents operating across linguistic boundaries, and synthetic organisms communicating in heterogeneous language environments, the canonical LDIR's English-centric design encounters a fundamental limitation: it cannot resolve intents expressed in Japanese, Spanish, Arabic, Mandarin, or any non-English language without a structured multilingual expansion architecture.

I present LDIR Expansions, a deterministic multilingual inference framework that extends the canonical LDIR to resolve natural-language intents across an arbitrary number of human languages while preserving the bit-identical determinism, certificate-anchored provenance, and governance-constrained execution that the Lume ecosystem requires. The framework introduces three architectural innovations: language-specific normalization modules that transform diverse natural-language inputs into a Universal Intent Schema (UIS) independent of any specific language; cross-lingual semantic equivalence verification that guarantees identical Intent Tuples for semantically equivalent expressions regardless of source language; and certificate-bound language routing that records the source language, the normalization path, and the equivalence verification result in the Trust Layer Certificate Fabric [3]. The framework integrates with the Lume compiler [1] through the expanded tolerance chain, with Lume-V [4] through language-aware envelope derivation, with DAIGS [5] through multilingual cognitive substrate extensions, with SOR through cross-lingual organism communication, and with GUPAS [2] through the six-layer governance architecture. I also identify and formalize six failure modes specific to multilingual deterministic inference—semantic collapse, over-normalization, under-normalization, conflicting constraints, cultural drift, and intent inversion—that must be detected and resolved at compile time. To my knowledge, this paper presents the first complete multilingual inference architecture for a deterministic natural-language programming ecosystem.

Keywords: LDIR, multilingual inference, deterministic compilation, cross-lingual resolution, semantic equivalence, natural-language programming, certificate-anchored transformation, Lume, GUPAS, Universal Intent Schema
1 Introduction
1.1 The Global Need for Multilingual Determinism
Software systems operate globally. A financial trading platform executes transactions across Tokyo, London, and New York. A medical diagnostic system serves practitioners in São Paulo, Lagos, and Mumbai. An autonomous logistics network coordinates warehouses in Shanghai, Rotterdam, and Los Angeles. In each of these scenarios, human operators express their computational intent in their native language—Japanese, Portuguese, Yoruba, Hindi, Mandarin, Dutch, Spanish—and expect the system to execute that intent with the same fidelity regardless of the language used. The conventional approach to multilingual computing treats language as a localization concern: the application's user interface is translated, but the underlying computation operates in a single language (typically English). This approach separates the human-facing layer from the computational layer, forcing non-English-speaking operators to work through a translation proxy that introduces latency, ambiguity, and potential misinterpretation.

The Lume programming language eliminates this separation by accepting natural-language expressions as direct compiler input [1]. English Mode, formalized in the companion paper on compile-time intent resolution [11], demonstrates that natural-language expressions can be compiled deterministically into canonical Abstract Syntax Trees. However, the current implementation is English-centric: the verb synonym tables, the parameter mapping tables, and the modifier classification tables are defined for English vocabulary. A Japanese-speaking programmer cannot write ファイルを作成してください (“please create a file”) and expect the compiler to resolve it through the same deterministic pipeline.

Multilingual determinism extends the Lume compiler's natural-language capability to all supported human languages. A deterministic multilingual compiler must guarantee that semantically equivalent expressions in different languages produce bit-identical Intent Tuples, regardless of the syntactic, morphological, and pragmatic differences between the source languages. This guarantee is the multilingual determinism invariant, and this paper formalizes the architecture that achieves it.

The demand for multilingual determinism is not speculative. The expansion of DAIGS across 22 domain verticals [5]—including Lume-Med, Lume-Fin, Lume-Agri, and Lume-Civ—creates operational scenarios where autonomous agents from different linguistic regions must coordinate deterministic actions. A Lume-Med agent in Tokyo and a Lume-Med agent in Berlin must resolve identical medical directives from Japanese and German inputs, respectively, to coordinate patient care across linguistic boundaries. Without multilingual determinism, cross-lingual coordination requires a human translation step that introduces latency, cost, and error risk.

1.2 Why LDIR Is Required for Cross-Lingual Intent Resolution
The LDIR provides the inference rulebook that governs how natural-language expressions are resolved into computational directives. The canonical LDIR specification defines 31 rules across 4 tiers: Tier 4 (Safety Rules, never overridden), Tier 3 (Axiom-Derived Rules, extended but not modified), Tier 2 (Domain Rules, domain-specific resolution strategies), and Tier 1 (Default Rules, fallback resolution strategies). These rules govern English Mode resolution through the seven-layer tolerance chain: exact match, fuzzy match, sentence splitting, pronoun resolution, temporal sequencing, logic block detection, and normalized AI fallback.

Cross-lingual intent resolution requires extending the LDIR at every tier. Tier 4 must include language-independent safety rules that prevent intent inversion regardless of source language. Tier 3 must include axiom-derived rules for the universal semantic categories that all human languages express (action, object, modifier, temporal relation, conditional logic). Tier 2 must include language-specific domain rules that handle the syntactic and morphological peculiarities of each supported language. Tier 1 must include multilingual fallback strategies that resolve expressions when language-specific rules fail.

The LDIR's tiered architecture is well suited for multilingual extension. The tiered structure ensures that language-universal safety rules (Tier 4) take absolute precedence over language-specific domain rules (Tier 2), preventing any language-specific peculiarity from overriding foundational safety constraints. This hierarchical safety guarantee is essential for multilingual determinism: no matter which language the programmer uses, the safety rules apply identically.

1.3 The Gap Between Translation and Inference
The conventional approach to multilingual computing is machine translation: translate the non-English input into English, then process the English translation through the standard pipeline. This approach is architecturally simple but fundamentally incompatible with deterministic compilation. Machine translation introduces probabilistic variance: the same source expression may produce different English translations depending on the translation model's version, the context window's contents, and the decoding strategy's random seed [14]. This variance is incompatible with the bit-identical determinism that the Lume ecosystem requires.

Even hypothetically perfect translation would be insufficient for deterministic multilingual inference. Translation preserves meaning at the natural-language level, but the LDIR operates at the computational intent level. Two natural-language expressions can be semantically equivalent in human communication but computationally distinct in the LDIR's resolution framework. The Japanese expression ファイルを消去しないでください (“please do not delete the file”) contains a negation structure (しないで, “shinaide”) that attaches to the verb differently than the English negation “do not delete.” A translation-based approach would translate the Japanese to English and then process the English through the negation detection system. A direct inference approach processes the Japanese negation structure through language-specific rules that map しないで directly to the canonical PRESERVE action, bypassing the translation step entirely.

Direct multilingual inference—processing each language through its own resolution pipeline that maps to the same Universal Intent Schema—eliminates the translation intermediary and its associated variance. Each language has its own normalization module, its own verb mapping table, and its own structural analysis rules, all producing the same canonical output format. The determinism guarantee applies within each language's pipeline and across languages through the cross-lingual equivalence verification.

1.4 Relationship to Lume, Trust Layer, DAIGS, SOR, and GUPAS
LDIR Expansions integrate with every layer of the Lume ecosystem. The Lume compiler [1] receives a new language-routing frontend that identifies the source language and dispatches the expression to the appropriate language normalization module. The Trust Layer [3] provides certificate-bound language provenance, recording the source language, the normalization module version, and the equivalence verification result in the Certificate Fabric. Lume-V [4] provides language-aware envelope enforcement, constraining multilingual compilations within the same deterministic safety boundaries used for English Mode compilations.

DAIGS [5] provides the cognitive substrate for multilingual agent coordination. When autonomous agents operating in different languages need to negotiate shared resources, the DAIGS arbitration engine evaluates their Intent Tuples—produced by different language pipelines but formatted in the same Universal Intent Schema—through the same deterministic conflict resolution logic. SOR provides the biological execution model within which multilingual organisms communicate through language-independent signal types, ensuring that organism-to-organism communication is deterministic regardless of the language in which each organism's cognitive substrate formulates its behavioral directives.

GUPAS [2] provides the governance framework within which multilingual compilations are validated. The six-layer governance architecture operates on canonical Intent Tuples, which are language-independent by construction. A governance policy that prohibits file deletion applies identically to a deletion intent expressed in English, Japanese, Arabic, or any other supported language, because the policy evaluates the canonical action (DELETE) rather than the source-language expression.

1.5 Overview of Contributions
This paper makes six primary contributions. First, I define the Universal Intent Schema (UIS), a language-independent intent representation format that serves as the target for all language-specific normalization modules. Second, I specify the language normalization module architecture, defining the structural contracts that each language module must satisfy to integrate with the LDIR expansion pipeline. Third, I formalize the cross-lingual semantic equivalence verification protocol, providing the mathematical guarantees that ensure equivalent expressions in different languages produce identical Intent Tuples. Fourth, I identify and classify six failure modes specific to multilingual deterministic inference. Fifth, I specify the integration architecture between LDIR Expansions and each component of the Lume ecosystem. Sixth, I provide security analysis demonstrating that the multilingual pipeline resists language-specific attack vectors including multilingual injection, semantic manipulation, and governance abuse through vocabulary exploitation.

The significance of this paper lies in its resolution of a tension that has been implicit in the Lume ecosystem since its inception: the tension between natural-language expressiveness (which is inherently multilingual) and deterministic compilation (which requires fixed resolution rules). LDIR Expansions resolve this tension by demonstrating that each language can have its own resolution rules while all languages converge on the same canonical output, achieving multilingual expressiveness and deterministic convergence simultaneously.

2 Foundations of LDIR
2.1 Deterministic Multilingual Inference
Deterministic multilingual inference is the property that a natural-language expression in any supported language, when processed through the LDIR expansion pipeline, produces a canonical Intent Tuple that is (a) bit-identical across all compilations of the same expression and (b) bit-identical to the Intent Tuple produced by the semantically equivalent expression in any other supported language. Property (a) is intra-language determinism; property (b) is cross-language determinism. Together, they constitute the multilingual determinism invariant.

Intra-language determinism is achieved through the same mechanisms used for English Mode [11]: version-locked vocabulary tables, ordered tolerance chains, and deterministic rule cascades. Each language's normalization module contains its own verb synonym table, parameter mapping table, and modifier classification table, all frozen at the compiler release version. The tolerance chain for each language follows the same seven-layer structure, with language-specific implementations at each layer.

Cross-language determinism requires an additional architectural component: the Universal Intent Schema. The UIS defines a language-independent representation for computational intent that all language normalization modules must produce. When two expressions in different languages produce the same UIS representation, they are guaranteed to produce the same canonical AST and the same Intent Tuple, because the UIS-to-AST mapping is language-independent and deterministic.

The multilingual determinism invariant is verifiable through a cross-lingual test corpus (§10.3 of the English Mode paper [11]) that contains expression pairs in all supported language combinations. Each pair is manually certified to express the same computational intent, and the test verifies that both expressions produce the same Intent Tuple hash. A failure in any pair triggers a review of the relevant language normalization modules.

2.2 Semantic Equivalence Across Languages
Semantic equivalence across languages is defined through the Universal Intent Schema: two expressions in different languages are semantically equivalent if and only if they map to the same UIS representation. This definition is mathematically precise and mechanically verifiable, avoiding the philosophical complexities of natural-language semantic equivalence in the linguistic sense [14]. The LDIR does not attempt to determine whether two expressions “mean the same thing” in the general cognitive sense; it determines whether they produce the same computational action within the Lume execution framework.

This computational definition of semantic equivalence is narrower than linguistic equivalence but more useful for deterministic compilation. Two expressions may be linguistically equivalent (conveying the same information to a human listener) but computationally distinct (producing different actions in the LDIR framework) because they differ in pragmatic implications that the LDIR resolves differently. Conversely, two expressions may be linguistically distinct (conveying different nuances to a human listener) but computationally equivalent (producing the same action) because the LDIR's normalization process abstracts away the linguistic nuances.

The narrowing of equivalence to computational equivalence is a deliberate design choice that serves the determinism guarantee. Attempting to achieve full linguistic equivalence would require probabilistic reasoning about pragmatic context, cultural conventions, and speaker intent—all of which are incompatible with deterministic compilation. By restricting equivalence to the computational domain, the LDIR achieves a verifiable, deterministic equivalence relation that is sufficient for the ecosystem's operational requirements.

2.3 Intent Normalization
Intent normalization for multilingual inference extends the English Mode normalization process [11] with language-specific preprocessing steps that account for the syntactic, morphological, and orthographic characteristics of each supported language. Japanese intent normalization includes morphological analysis (segmenting continuous text into words, since Japanese does not use spaces between words), particle identification (identifying grammatical particles like を, に, で that signal object, destination, and location roles), and honorific stripping (removing politeness markers like ください that carry social meaning but no computational intent).

Arabic intent normalization includes right-to-left text direction normalization, diacritical mark processing (short vowels are often omitted in written Arabic, creating ambiguity that requires deterministic resolution), root extraction (Arabic words are typically derived from three-consonant roots, and the root extraction process maps inflected forms to canonical action verbs), and definite article handling (the Arabic definite article ال attaches to the following word, requiring segmentation before verb identification).

Mandarin intent normalization includes character-level tokenization (since Mandarin does not use spaces between words), measure word identification (Mandarin requires measure words between numbers and nouns, which must be recognized and stripped for computational normalization), tonal disambiguation (homophones that differ only in tone must be disambiguated through context), and Classical Chinese construct detection (formal Mandarin sometimes uses Classical Chinese grammatical structures that require special parsing rules).

Each language's normalization module produces an intermediate representation in the Universal Intent Schema format. The UIS format is identical regardless of the source language: a canonical action verb (from the universal action verb vocabulary), canonical parameters (from the universal parameter schema), and canonical modifiers (from the universal modifier classification). This convergence point ensures that all downstream processing—AST mapping, certificate emission, envelope derivation—operates on a language-independent representation.

2.4 Canonical AST Mapping
Canonical AST mapping for multilingual inference is identical to English Mode AST mapping: the UIS representation is transformed into the deterministic Abstract Syntax Tree format defined by the Lume compiler specification [6]. Because all language normalization modules produce the same UIS format, the AST mapping logic is shared across all languages. There is no Japanese-specific AST mapping or Arabic-specific AST mapping; all languages converge on the UIS, and the UIS maps to the AST through a single, language-independent mapping function.

This architectural decision—converging all languages to a universal intermediate representation before AST mapping—is critical for cross-lingual determinism. If different languages mapped directly to ASTs through language-specific logic, the risk of cross-lingual divergence would increase with each language added. By funneling all languages through the UIS, the cross-lingual determinism guarantee reduces to two verifiable properties: (1) each language's normalization correctly maps to the UIS, and (2) the UIS-to-AST mapping is deterministic. Property (1) is verified per-language through language-specific test corpora. Property (2) is verified once through the canonical determinism test corpus.

The AST produced by multilingual compilation is indistinguishable from the AST produced by English Mode compilation. A program compiled from Japanese input executes identically to the same program compiled from English input, provided the Japanese and English expressions are semantically equivalent in the UIS sense. This indistinguishability extends to certification: the COMPILE_ROOT certificate records the AST hash, which is identical regardless of source language.

2.5 Certificate-Anchored Transformations
Every transformation in the LDIR multilingual pipeline is anchored to a certificate in the Trust Layer Certificate Fabric [3]. The language identification step produces a LANGUAGE_ID certificate recording the detected source language and the detection confidence (1.0 for explicitly declared languages, lower for auto-detected languages). The normalization step produces a NORMALIZATION certificate recording the normalization module version, the input hash, and the UIS output hash. The equivalence verification step (when applicable) produces an EQUIVALENCE certificate recording the compared language pairs and the hash comparison result.

Certificate-anchored transformations enable forensic analysis of multilingual compilations. When a multilingual compilation produces unexpected results, the investigator can trace the certificate chain to determine at which transformation stage the unexpected result was introduced. If the LANGUAGE_ID certificate shows an incorrect language detection, the error originated at the routing stage. If the NORMALIZATION certificate shows a correct UIS output but the COMPILE_ROOT certificate shows an unexpected AST hash, the error originated at the AST mapping stage.

The certificates also enable cross-lingual audit. A governance authority can query the Certificate Fabric for all compilations in a specific language, enabling language-specific quality analysis. If Japanese compilations consistently produce more arbitration certificates than English compilations, the discrepancy may indicate that the Japanese normalization module's verb mapping table requires expansion. This language-specific telemetry is essential for maintaining consistent compilation quality across all supported languages.

3 The Challenge of Multilingual Determinism
3.1 Semantic Drift Across Languages
Semantic drift across languages occurs when the meaning of a translated term shifts relative to the original language's meaning in a way that alters the computational intent. The English verb “set” maps to the canonical action SET (assignment). The Japanese equivalent 設定する (“settei suru”) carries a connotation of “configuring” or “establishing” that is broader than simple assignment. If the Japanese normalization module maps 設定する to SET without accounting for the broader connotation, some Japanese expressions may resolve to SET when the programmer intended CONFIGURE—a different canonical action with different parameter requirements.

Semantic drift is managed through language-specific verb mapping tables that are carefully curated by linguists and domain experts familiar with each language's programming conventions. The Japanese verb mapping table maps 設定する to SET for simple assignment contexts (設定する followed by a value parameter) and to CONFIGURE for complex configuration contexts (設定する followed by a parameter group). This context-dependent mapping is specified in the LDIR Tier 2 domain rules for Japanese and is version-locked to the compiler release.

The version-locking strategy ensures that semantic drift between languages does not cause surprise divergence between compiler versions. A Japanese expression that maps to SET in version 1.1 will map to SET in every compilation under version 1.1, regardless of evolving language conventions. When a compiler update modifies the Japanese verb mapping, the migration analysis tool (§11.5 of the English Mode paper [11]) alerts users to resolution changes, enabling proactive adaptation.

3.2 Cultural and Contextual Variance
Human languages encode cultural assumptions that influence computational interpretation. Japanese business communication employs hierarchical politeness levels that can alter the urgency and authority of a directive. The expression お願いします (“onegai shimasu,” a polite request) and してください (“shite kudasai,” a direct instruction) both express the same computational action—execute the specified operation—but carry different social register. A multilingual deterministic compiler must strip the social register without altering the computational intent.

Arabic's distinction between formal (Modern Standard Arabic, MSA) and colloquial dialects creates a related challenge. A programmer writing in Egyptian Arabic may use dialectal verb forms that differ from MSA forms. The LDIR normalization module for Arabic must recognize both MSA and major dialectal variants, mapping all to the same canonical action verbs. This dialect normalization is specified in the Arabic language module's variant mapping table, which includes entries for Egyptian, Gulf, Levantine, and Maghrebi Arabic dialectal forms.

Cultural variance extends to number formatting, date conventions, and measurement systems. Japanese expressions may specify dates in year-month-day format; American English expressions use month-day-year. Arabic expressions may use Eastern Arabic numerals (٠١٢) rather than Western Arabic numerals (012). The normalization module for each language handles these cultural conventions through format-specific parsing rules that convert culturally formatted values to canonical representations before UIS emission.

3.3 Ambiguity Propagation
Ambiguity in the source language can propagate through the multilingual pipeline, producing resolution failures or incorrect resolutions at the UIS stage. Different languages have different ambiguity profiles: English is heavily polysemous (many words have multiple meanings), Japanese relies heavily on context for pronoun resolution (personal pronouns are frequently omitted), Mandarin uses tonal distinctions that are lost in written text, and Arabic's consonantal root system creates systematic morphological ambiguity.

Ambiguity propagation is mitigated through language-specific disambiguation rules at each layer of the tolerance chain. English polysemy is resolved through the verb synonym table's context-dependent mappings. Japanese pronoun omission is resolved through the context stack's most-recent-antecedent rule, adapted for Japanese syntax (which places the verb at the end of the sentence, requiring backward scanning for the subject). Mandarin tonal ambiguity in written text is resolved through character-level context analysis (surrounding characters disambiguate homophones through established collocations). Arabic morphological ambiguity is resolved through root pattern matching against the canonical action verb table.

When language-specific disambiguation fails, the expression is routed to the language's AI fallback layer (Layer 7 of the tolerance chain). The fallback layer for each language operates within the same deterministic constraints as the English fallback: it applies a normalized, version-locked evaluation function rather than a probabilistic model. If the fallback layer also fails, the compiler emits a language-specific HALT diagnostic in the source language, guiding the programmer toward an unambiguous reformulation.

3.4 Deterministic Constraints
The deterministic constraints for multilingual inference extend the English Mode constraints with language-specific requirements. The canonical ordering constraint requires that AST construction follows the same fixed traversal order regardless of source language. The hash binding constraint requires that the AST hash is computed from the same canonical serialization regardless of the source language's text direction (left-to-right for English, right-to-left for Arabic, top-to-bottom for traditional Japanese). The certificate chain constraint requires that every multilingual compilation produces a complete certificate chain that includes the source language identification.

Language-specific deterministic constraints address structural properties unique to each language. Japanese compound verbs (e.g., 読み込む, “yomkomu,” “to read into/load”) must be decomposed into their component verbs and resolved atomically before composition. Arabic broken plurals (irregular plural forms that do not follow predictable patterns) must be mapped to canonical singular forms through a static irregular plural table. Mandarin serial verb constructions (multiple verbs in sequence expressing a single complex action) must be parsed through a serial verb detection rule that identifies the construction boundary.

These language-specific constraints are encoded in each language's normalization module and are evaluated before the UIS emission stage. The constraint evaluation is deterministic: the same input expression evaluates the same constraints in the same order, producing the same pass/fail verdict. Constraint violations are reported as compile-time errors in the source language, following the same diagnostic format used for English Mode constraint violations.

4 The LDIR Expansion Pipeline
4.1 Lexical Normalization
Lexical normalization for multilingual inference extends the English Mode normalization [11] with language-specific preprocessing. The first step is script detection: the normalizer identifies the writing system of the input (Latin, CJK, Arabic, Devanagari, Cyrillic, and others) using Unicode block analysis. The script detection determines which language normalization module handles the expression. When the script is ambiguous (Latin script is used by English, Spanish, French, German, and many other languages), the normalizer applies a language identification classifier that examines vocabulary frequency patterns to select the most likely language.

Language identification is deterministic: the classifier uses a static decision tree trained on vocabulary frequency tables that are frozen at compiler release. The decision tree evaluates character n-gram frequencies, function word presence, and diacritical mark patterns to produce a single language classification. The classification is verified through the LANGUAGE_ID certificate, which records the classification result and the features that determined it.

After language identification, the normalizer applies language-specific lexical transformations. For Japanese: morphological segmentation using a deterministic dictionary-based tokenizer (not a statistical model). For Arabic: diacritical mark normalization, definite article segmentation, and right-to-left text reordering to a canonical internal representation. For Mandarin: character-level tokenization and measure word identification. For Spanish: diacritical mark preservation (á, é, í, ó, ú carry distinct phonological meaning), inverted punctuation handling (¿, ¡), and clitic pronoun attachment analysis. Each language's lexical normalization is specified in the language module's normalization specification and is version-locked to the compiler release.

4.2 Semantic Grounding
Semantic grounding for multilingual inference maps language-specific tokens to canonical meaning structures through language-specific verb synonym tables, object keyword tables, and modifier classification tables. Each language's tables are curated independently, mapping the language's vocabulary directly to the universal canonical action verbs, object types, and modifier categories. The tables are not derived from English tables through translation; they are constructed from each language's own linguistic analysis.

This direct construction approach avoids the Translation Intermediary Problem: English-centric tables would encode English's semantic distinctions and miss distinctions that other languages make. Japanese distinguishes between 作る (“tsukuru,” to create/make by hand) and 作成する (“sakusei suru,” to create formally/systematically). Both map to the canonical CREATE action, but the distinction could be preserved as a modifier parameter if the domain requires it. The Japanese verb synonym table encodes this distinction directly, without routing through an English intermediary that would collapse the distinction.

Semantic grounding for agglutinative languages (Japanese, Turkish, Finnish) requires morphological decomposition before verb identification. The grounded representation must separate the verb stem from its inflectional suffixes, identify the canonical action from the verb stem, and extract modifier information from the suffixes. For fusional languages (Arabic, Spanish, Russian), the grounding process must handle stem changes that encode tense, aspect, mood, and person, extracting the canonical action from the modified stem through root pattern matching.

The output of the semantic grounding stage is a language-independent UIS structure. At this point, the source language information is no longer needed for resolution; the expression has been fully grounded in the universal canonical vocabulary. The NORMALIZATION certificate records the transition from language-specific tokens to language-independent UIS, enabling forensic verification that the grounding was performed correctly.

4.3 Cross-Lingual Constraint Extraction
Cross-lingual constraint extraction derives envelope constraints from the UIS representation using the same constraint extraction logic applied to English Mode compilations [11]. Because the UIS representation is language-independent, the constraint extraction stage is shared across all languages. The resource profiles, state mutation specifications, and temporal constraint derivations operate on canonical action types, which are identical regardless of the source language.

Cross-lingual constraint extraction introduces one additional consideration: language-specific pragmatic constraints. Some languages encode pragmatic information that has computational implications. The Japanese expression 必ず (“kanarazu,” “without fail/absolutely”) modifying an action implies a stricter reliability requirement than the default. The Arabic expression إن شاء الله (“insha'Allah,” used idiomatically rather than religiously) modifying an action implies a conditional or aspirational quality. These pragmatic modifiers are captured by the language-specific grounding stage and encoded as UIS modifier parameters, enabling the constraint extraction stage to adjust envelope parameters accordingly.

The pragmatic constraint handling is conservative: when a pragmatic modifier implies stricter requirements, the envelope is narrowed. When a pragmatic modifier implies loosened requirements, the modifier is flagged but the envelope is not relaxed beyond the canonical default. This conservative approach follows the expansion architecture's one-directional composition rule [10]: expansion (including multilingual expansion) narrows, never widens.

4.4 Intent Tuple Harmonization
Intent tuple harmonization is the process of ensuring that the Intent Tuple produced by a multilingual compilation is structurally identical to the Intent Tuple that would be produced by the semantically equivalent English Mode compilation. Harmonization verifies five fields: the intent source (stored in the source language, not translated), the intent hash (computed from the UIS representation, not from the source-language text), the resolved action (expressed in canonical action vocabulary), the trust binding (the compiler's certificate, language-independent), and the envelope constraint (derived from the UIS, language-independent).

The key harmonization decision is the intent hash computation. The hash is computed from the UIS representation rather than from the source-language text. This design ensures that semantically equivalent expressions in different languages produce identical hashes, because they produce identical UIS representations. The source-language text is preserved in the intent source field for forensic purposes but does not participate in the hash computation. This separation enables the hash to serve as a language-independent intent identifier while preserving the original expression for human review.

Harmonization also verifies that the resolved action field is expressed in the universal canonical action vocabulary, not in any language-specific vocabulary. A Japanese compilation that produces a resolved action containing Japanese characters has failed harmonization and must be rejected. This verification catches normalization errors where the language module emits partially normalized output that contains residual language-specific tokens.

4.5 Canonical AST Mapping
Canonical AST mapping for multilingual compilations is identical to English Mode AST mapping [11]: the UIS representation is transformed into the deterministic AST using the action-to-AST table. The mapping function is language-independent; it operates on UIS representations that contain no language-specific information. A UIS representation containing CREATE_FILE(name="report.txt") maps to the same AST node structure regardless of whether the original expression was in English, Japanese, Arabic, or Mandarin.

The language-independence of AST mapping is a direct consequence of the UIS convergence architecture. All language-specific processing occurs before UIS emission; all language-independent processing occurs after UIS emission. The UIS serves as a firewall that prevents language-specific information from leaking into the compilation's downstream stages. This firewall ensures that the runtime, the governance layer, and the certification layer never need to be aware of the source language—they operate on canonical ASTs that are identical regardless of linguistic origin.

The AST mapping produces the same hash for identical UIS inputs, enabling the cross-lingual equivalence verification. Two compilations from different languages that produce the same UIS representation (verified by UIS hash comparison) are guaranteed to produce the same AST hash. This transitive guarantee—same UIS implies same AST implies same execution—is the mathematical foundation of cross-lingual determinism.

4.6 Certificate-Bound Validation
Certificate-bound validation for multilingual compilations extends the English Mode validation [11] with language-specific certificates. The validation stage produces four certificates: LANGUAGE_ID (recording the detected source language), NORMALIZATION (recording the language module version and the UIS output hash), COMPILE_ROOT (recording the AST hash and the output hash), and optionally EQUIVALENCE (recording the cross-lingual equivalence verification result when the same intent has been compiled from multiple languages).

The certificate chain for a multilingual compilation is longer than the chain for an English Mode compilation (four certificates vs. three), reflecting the additional language identification and normalization steps. The additional certificate provides the forensic information needed to trace multilingual compilation issues: if a Japanese compilation produces an unexpected result, the investigator can examine the LANGUAGE_ID certificate to verify that the input was correctly identified as Japanese, the NORMALIZATION certificate to verify that the Japanese normalization module produced the expected UIS output, and the COMPILE_ROOT certificate to verify that the UIS-to-AST mapping produced the expected result.

The governance validation during certificate-bound validation is language-independent. The governance layer evaluates the canonical action (from the UIS) against policy constraints, without reference to the source language. A governance policy that prohibits file deletion applies identically to English, Japanese, Arabic, and Mandarin compilations, because the policy evaluates the canonical DELETE action, not the source-language verb. This language-independent governance enforcement is essential for maintaining consistent security across multilingual deployments.

5 Multilingual Intent Arbitration
5.1 Conflicting Interpretations
Multilingual intent arbitration handles two categories of conflicts: intra-language conflicts (multiple valid interpretations of a single expression within one language) and inter-language conflicts (expressions from different languages that, despite being intended as equivalent, produce different UIS representations due to normalization differences). Intra-language conflicts are resolved through the same priority rules used for English Mode arbitration [11]. Inter-language conflicts require a specialized cross-lingual arbitration mechanism.

Inter-language conflicts arise when the UIS representations produced by different language modules for intended-equivalent expressions diverge. A Japanese programmer writes データを更新する (“update the data”) and an English programmer writes “refresh the data.” The Japanese module maps 更新する to UPDATE; the English module maps “refresh” to RELOAD. UPDATE and RELOAD are different canonical actions with different state mutation profiles. If these expressions are intended to coordinate the same operation, the inter-language conflict must be detected and resolved.

Inter-language conflict detection operates through the EQUIVALENCE certificate mechanism. When a coordination protocol designates two expressions from different languages as intended-equivalent (through a session certificate that binds them), the equivalence verification compares their UIS hashes. A hash mismatch triggers inter-language arbitration, which evaluates the conflicting UIS representations against the cross-lingual arbitration rules to determine which canonical action the coordinated operation should use.

5.2 Priority Rules
Multilingual arbitration priority rules extend the English Mode priority rules [11] with language-awareness. The extended priority hierarchy is: (1) safety (Tier 4 rules, language-independent), (2) specificity (the interpretation with more resolved parameters), (3) canonical precedence (the canonical action with the lower ordinal in the universal action vocabulary), (4) language seniority (the language with the longer operational history in the ecosystem, used as a tiebreaker for inter-language conflicts), and (5) envelope safety (the interpretation with the smaller envelope footprint).

Language seniority is a controversial tiebreaker that requires justification. When two languages produce genuinely different UIS representations for intended-equivalent expressions, one representation must be selected. Language seniority selects the representation from the language with more accumulated inference patterns in the Evolver's global pattern database, on the rationale that a more mature language module is more likely to have converged on correct canonical mappings. This tiebreaker is a pragmatic compromise; the ideal resolution is to update the less mature language module to match the more mature module's mapping.

The safety tiebreaker remains the ultimate fallback, identical to English Mode: when all other factors are tied, the interpretation with the smaller envelope footprint is selected. This universal safety preference ensures that multilingual arbitration never selects a more powerful interpretation over a less powerful one when all other factors are equal.

5.3 Envelope Constraints
Envelope constraints participate in multilingual arbitration by eliminating interpretations that would violate the compilation context's safety boundaries. The envelope constraint filter operates on the UIS representation, which is language-independent. Therefore, the envelope filtering logic is shared across all languages: the same filter that eliminates unsafe interpretations for English compilations eliminates unsafe interpretations for Japanese, Arabic, and Mandarin compilations.

Language-specific pragmatic constraints (§4.3) may influence the envelope derivation, but the derived envelope is always expressed in the universal envelope format (resource limits, state mutation scope, interaction boundaries, temporal constraints). This universal format ensures that envelope constraints are comparable across languages, enabling the arbitration mechanism to evaluate competing interpretations from different languages against the same safety criteria.

The envelope constraint filter provides a language-independent security guarantee: an operator who is prohibited from performing a specific action cannot circumvent the prohibition by switching to another language. The prohibition is enforced on the canonical action, not on the source-language expression. This language-independent enforcement is critical for preventing governance evasion through language switching.

5.4 Arbitration Certificates
Every multilingual arbitration decision is recorded in an Arbitration Certificate that extends the English Mode arbitration certificate with language-specific fields. The multilingual Arbitration Certificate records the source languages of the competing interpretations, the UIS representations of each interpretation, the cross-lingual arbitration rules applied, and the selected interpretation. For inter-language arbitrations, the certificate also records the language seniority scores and the divergent canonical mappings that triggered the conflict.

Multilingual Arbitration Certificates feed a specialized language quality analytics pipeline. The pipeline tracks arbitration frequency per language pair, identifying language combinations that frequently produce inter-language conflicts. High-conflict language pairs indicate normalization module divergence that should be addressed through vocabulary table reconciliation. This feedback mechanism drives continuous improvement of the multilingual inference quality.

The certificates also enable regulatory compliance for cross-border operations. When a financial transaction is compiled from Japanese in Tokyo and the same transaction is compiled from English in New York, the Arbitration Certificate demonstrates that both compilations produced the same canonical action, satisfying regulatory requirements for cross-border transaction consistency.

5.5 Deterministic Finalization
Deterministic finalization for multilingual compilations follows the same process as English Mode finalization [11]: the arbitration decision is committed, the Intent Tuple is sealed, the canonical AST is generated, and the complete certificate chain is emitted. The finalization stage performs a cross-lingual determinism verification: the compiler re-normalizes the source expression and compares the resulting UIS hash against the hash recorded in the Intent Tuple. If the hashes match, the compilation is confirmed deterministic.

For inter-language arbitrations, the finalization stage also records the resolution outcome in the Evolver's cross-lingual pattern database. This recording enables the Evolver to detect systematic inter-language divergences and recommend vocabulary table reconciliation to the language module maintainers. The Evolver does not automatically modify vocabulary tables; it provides recommendations that human curators review and apply through the standard governance process.

The finalized compilation artifact is identical in format regardless of source language. A finalized Japanese compilation and a finalized English compilation contain the same types of certificates, the same AST format, and the same envelope specification. The only language-specific information in the finalized artifact is the intent source field (preserving the original expression) and the LANGUAGE_ID certificate (recording the source language). All other components are language-independent.

6 Integration with Lume
6.1 AST Determinism
LDIR Expansions produce the same canonical AST format as the English Mode frontend. The AST node vocabulary, construction order, serialization protocol, and hash computation are identical across all language frontends. A program compiled from Japanese input is indistinguishable from the same program compiled from English input at the AST level. This indistinguishability is verified through the cross-lingual equivalence test corpus, which compiles semantically equivalent expressions in all supported language pairs and verifies AST hash identity.

AST determinism across languages enables a powerful quality assurance technique: cross-lingual regression testing. A corpus of documented operations expressed in multiple languages can be re-compiled after every normalization module update to detect regressions. Any expression pair that produced matching AST hashes before the update but divergent hashes after indicates a normalization regression in one of the affected language modules.

The cross-lingual regression testing framework operates within the standard continuous integration pipeline. Each compiler build includes a multi-language compilation stage that processes the cross-lingual test corpus and reports any hash divergences. This automated verification ensures that AST determinism across languages is continuously maintained as language modules evolve.

6.2 Grammar Constraints
Grammar constraints for multilingual compilation ensure that each language can express exactly the computational constructs that Lume's structured syntax can express—no more, no fewer. This constraint parity is achieved through the UIS, which defines a fixed set of representable actions, parameters, and modifiers. Each language's normalization module maps the language's vocabulary to the UIS vocabulary, and the UIS vocabulary maps one-to-one to the Lume grammar's computational constructs.

Grammar constraint parity across languages is verified through coverage analysis. For each canonical action verb in the UIS vocabulary, each language's verb synonym table must contain at least one mapping. For each canonical parameter type, each language's parameter mapping table must contain at least one mapping. Coverage gaps indicate incompletely implemented language modules and are reported as compilation warnings when the language module is loaded.

Grammar constraints also prevent language-specific capabilities that do not exist in the universal vocabulary. If a language module's verb table maps a language-specific verb to a canonical action that does not exist in the UIS vocabulary, the mapping is rejected during module validation. This rejection ensures that one language cannot express capabilities that other languages cannot, maintaining the symmetry of the multilingual ecosystem.

6.3 Runtime Compatibility
Multilingual-compiled programs execute within the standard Lume runtime without modification. The runtime receives a canonical AST—produced through the language-independent AST mapping function—and executes it according to the standard deterministic execution semantics. The runtime does not know and cannot determine the source language of the AST it executes. This opacity is deliberate and ensures that runtime behavior is identical for all source languages.

Runtime compatibility extends to every runtime subsystem: SOR cell management, Signal Bus communication, homeostatic regulation, and multi-agent coordination. A Japanese-compiled program and an English-compiled program executing in adjacent SOR cells communicate through the same Signal Bus, following the same signal protocols, with no language-specific adaptation required. The signals themselves are expressed in canonical format, not in any natural language.

This runtime opacity provides a strong guarantee against language-based discrimination in multi-tenant environments. Agents compiled from different languages operate on a level playing field, receiving identical resource allocation, identical governance treatment, and identical performance characteristics. No agent can determine or influence the source language of another agent's compiled program.

6.4 Canonicalization Rules
Canonicalization rules for multilingual compilation govern the transformation from language-specific intermediate representations to the Universal Intent Schema. Each language module's canonicalization rules specify how the language's grammatical structures map to UIS structures. Japanese SOV (Subject-Object-Verb) word order maps to UIS action-object order through a reordering rule. Arabic VSO (Verb-Subject-Object) word order maps through a different reordering rule. English SVO (Subject-Verb-Object) word order maps through the canonical rule.

The canonicalization rules are idempotent: applying the rules to an already-canonical UIS representation produces the same UIS representation. This property is verified through a dedicated test suite for each language module. Idempotency ensures that double-canonicalization (which can occur during verification processes) does not alter the output.

The canonicalization rules are co-versioned with the LDIR rulebook and the language-specific vocabulary tables. When any component of the multilingual pipeline is updated, all co-versioned components are updated simultaneously, preventing the subtle divergence that could occur if components evolved independently. The co-versioning is enforced through the Trust Layer certification process, which validates version consistency before issuing the compiler's certification certificate.

7 Integration with Trust Layer
7.1 Certificate-Bound Multilingual Intent
Every multilingual compilation produces a certificate chain that binds the source-language expression to the compiled executable through the Trust Layer Certificate Fabric [3]. The chain consists of four certificates: LANGUAGE_ID, NORMALIZATION, RESOLUTION (recording the tolerance chain path), and COMPILE_ROOT. Together, these certificates provide a complete, cryptographically verifiable record of the multilingual compilation process, from language identification through canonical AST emission.

The extended certificate chain enables language-specific forensic analysis. An investigator can query the Certificate Fabric for all LANGUAGE_ID certificates with a specific language value, retrieving the complete compilation history for that language. This query capability enables statistical analysis of per-language compilation success rates, arbitration frequencies, and failure mode distributions, informing language module quality improvement efforts.

Certificate-bound multilingual intent also supports cross-border regulatory compliance. When a governance authority requires proof that a specific computational action was authorized by a specific human operator in a specific language, the certificate chain provides that proof. The LANGUAGE_ID certificate confirms the source language. The NORMALIZATION certificate confirms the resolution path. The COMPILE_ROOT certificate confirms the resulting executable action. This end-to-end provenance trail satisfies the documentation requirements of international regulatory frameworks.

7.2 Identity Anchoring
Multilingual compilations are anchored to the compiling entity's identity through the same Ed25519 certificate chain used for English Mode compilations. The entity's identity certificate is language-independent; an operator's identity does not change when they switch languages. This language-independence ensures that identity tracking is consistent across language switches, preventing an operator from evading accountability by compiling in a different language.

Identity anchoring also applies to language normalization modules. Each language module receives its own identity certificate, issued by the designated Ecosystem Governance Authority. The module's certificate is included in the NORMALIZATION certificate chain, enabling forensic verification that a specific normalization was performed by a specific, authorized version of a specific language module. This module-level identity anchoring enables precise attribution when a normalization error is identified.

The identity anchoring mechanism ensures that unauthorized language modules cannot process expressions. A rogue language module that is not certified by the designated Ecosystem Governance Authority will be rejected by the Trust Layer validators, because its identity certificate does not chain to the ecosystem's root authority. This enforcement prevents the introduction of malicious normalization logic through unauthorized language modules.

7.3 Provenance and Auditability
The multilingual pipeline produces a complete provenance trail that extends the English Mode provenance trail with language-specific information. The trail includes the detected source language, the language module version, the normalization path (which morphological analysis rules were applied, which verb mappings were activated, which disambiguation strategies were used), and the UIS output. This trail is permanent and cryptographically sealed in the Certificate Fabric.

Auditability extends to cross-lingual equivalence. When two compilations from different languages are designated as intended-equivalent, the EQUIVALENCE certificate records the comparison result. A governance auditor can query the Certificate Fabric for all EQUIVALENCE certificates with a MISMATCH result, identifying intended-equivalent expressions that actually diverged—indicating either a normalization error or a misidentified equivalence.

The provenance and auditability mechanisms enable a form of multilingual compliance verification. An organization operating in multiple countries can demonstrate to each country's regulatory authority that computational actions taken in the local language are equivalent to actions taken in the organization's corporate language, using the EQUIVALENCE certificates as formal evidence of cross-lingual consistency.

7.4 Governance Constraints
The Trust Layer imposes governance constraints on multilingual compilations through the same governance policy framework used for English Mode compilations. Governance policies operate on canonical actions, which are language-independent. A policy that prohibits file deletion prohibits the DELETE action regardless of the source language that expressed it. This language-independent policy enforcement is a direct consequence of the UIS convergence architecture.

Language-specific governance constraints can be introduced through the Governance Expansion Subsystem [10]. An organization operating in a regulated industry might require that all compilations in a specific language undergo additional review (for example, requiring that all Arabic compilations in a financial context be reviewed by an Arabic-speaking compliance officer). These language-specific governance requirements are encoded as expansion governance policies and enforced during the certificate-bound validation stage.

Governance constraints also prevent language-based governance evasion. An operator who is prohibited from performing a specific action in English is equally prohibited from performing that action in any other language. The governance layer does not evaluate the source-language expression; it evaluates the canonical action, which is identical regardless of the source language. This canonical evaluation prevents the attack vector of encoding prohibited actions in languages that the governance authority does not understand.

8.1 Envelope Constraints on Multilingual Intent
Lume-V [4] provides envelope enforcement for multilingual compilations through the same mechanism used for English Mode compilations. This language-blindness ensures that envelope enforcement is consistent across all languages.

Language-specific pragmatic constraints (§4.3) may result in tighter envelope derivations for some languages. This asymmetry is acceptable because the one-directional composition rule ensures that the stricter envelope is always within the bounds of the canonical envelope—it provides stronger safety guarantees, never weaker.

The envelope derivation for multilingual compilations is deterministic: the same UIS representation always produces the same envelope, and the same source-language expression always produces the same UIS representation (through the language module's deterministic normalization). The composition of these two deterministic functions produces end-to-end deterministic envelope derivation from source-language expression to enforcement parameters.

8.2 Safety Boundaries
Safety boundaries for multilingual programs are identical to safety boundaries for English Mode programs. The safety boundary mechanism operates at the runtime level, after all language-specific processing has completed. Lume-V participates in multilingual arbitration by providing envelope information that influences the arbitration decision, following the same pattern as English Mode arbitration [11]. For inter-language arbitrations, the Lume-V envelope provides an additional disambiguation mechanism. If one canonical action requires network access and the other does not, and the compilation context's envelope prohibits network access, the envelope filter eliminates the network-requiring interpretation, resolving the inter-language conflict without invoking the priority rules.

This envelope-based disambiguation is language-neutral: it does not favor one language over another but rather favors interpretations that are compatible with the operational environment. The environmental compatibility criterion is a natural extension of the safety preference principle that governs all arbitration in the Lume ecosystem.

8.4 Runtime Enforcement
Lume-V runtime enforcement for multilingual programs is identical to enforcement for English Mode programs. The wrapper intercepts all system calls, memory allocations, and network requests, validating each against the derived envelope constraints. Runtime enforcement data collected from multilingual programs feeds language-specific quality analytics. These per-language metrics inform the continuous improvement of language normalization modules. 11 Failure Modes in Multilingual Inference
11.1 Semantic Collapse
Semantic collapse occurs when a language's normalization module maps multiple distinct computational concepts to the same canonical action, losing semantic distinctions that the source language preserves. Japanese distinguishes between コピーする (“copy suru,” to copy/duplicate) and 複製する (“fukusei suru,” to replicate/reproduce). If both map to the same canonical COPY action, the distinction is lost. If the domain requires the distinction (for example, in a manufacturing context where “copy” means duplicate a document and “replicate” means manufacture a physical replica), the collapse produces incorrect normalizations.

Semantic collapse is detected through domain-specific distinction analysis: the language module's vocabulary table is compared against the domain's canonical action vocabulary to identify mappings where multiple source-language terms map to the same canonical action. Detected collapses are reported as vocabulary coverage warnings, and the domain's canonical action vocabulary can be extended through the Intent Expansion Subsystem [10] to introduce a new canonical action (REPLICATE) that preserves the distinction.

The distinction between acceptable collapse and problematic collapse depends on the operational domain. In a generic computing context, コピーする and 複製する mapping to the same COPY action is acceptable. In a manufacturing domain, the collapse is problematic. The LDIR Expansion architecture supports domain-specific vocabulary extensions through the Tier 2 domain rules, enabling per-domain collapse resolution without modifying the generic vocabulary.

11.2 Over-Normalization
Over-normalization occurs when the normalization module strips meaningful information from the source-language expression during the normalization process. Japanese politeness levels, Arabic rhetorical emphasis markers, and Spanish subjunctive mood indicators all carry information that a human listener would use to calibrate the urgency, certainty, or formality of the directive. If the normalization module strips all of this information, the resulting UIS representation may lack context that the programmer intended to convey.

Over-normalization is managed through the modifier preservation principle: language-specific modifiers that have computational implications (urgency, reliability requirements, conditionality) are preserved as UIS modifier parameters, while language-specific modifiers that have only social implications (politeness, formality, rhetorical emphasis) are stripped. The classification of each modifier as “computationally relevant” or “socially relevant” is specified in the language module's modifier classification table.

The modifier classification is inherently judgment-dependent and must be reviewed by linguists who understand both the source language's pragmatics and the Lume ecosystem's computational semantics. Misclassification—treating a computationally relevant modifier as socially relevant, or vice versa—can produce subtle normalization errors that are difficult to detect through automated testing. The cross-lingual equivalence corpus helps detect these errors by comparing the normalization outputs of expressions that differ only in the contested modifier.

11.3 Under-Normalization
Under-normalization occurs when the normalization module fails to resolve language-specific constructs into canonical form, passing residual language-specific tokens to the UIS emission stage. Under-normalization is detected by the UIS validator, which checks that the UIS representation contains only canonical vocabulary tokens. Any non-canonical token triggers a normalization failure error.

Under-normalization is more common in morphologically complex languages where the normalization module must decompose compound forms before mapping to canonical actions. Turkish agglutinative verb forms can encode subject, object, tense, aspect, mood, and negation in a single word (e.g., “yapamayacaklarmış” encodes at least five grammatical categories). If the morphological decomposition fails to identify all components, the residual undecomposed form passes to the UIS stage as a non-canonical token.

Under-normalization is addressed through comprehensive morphological rule coverage for each language and through fallback decomposition strategies that attempt to isolate the canonical verb root even when the full morphological analysis fails. The fallback strategy produces a best-effort normalization with a provenance flag indicating partial decomposition, enabling the programmer to review and refine the expression.

11.4 Conflicting Constraints
Conflicting constraints in multilingual inference occur when language-specific pragmatic constraints conflict with canonical envelope constraints or with pragmatic constraints from another language. A Japanese expression modified by 必ず (“without fail”) implies a strict reliability requirement, while the same operation coordinated with a Spanish expression modified by “si es posible” (“if possible”) implies a best-effort requirement. These pragmatic constraints conflict when the two expressions are intended to coordinate the same operation.

Cross-lingual constraint conflicts are detected during the intent tuple harmonization stage (§4.4), which compares the derived envelope constraints of intended-equivalent expressions. If the constraints conflict, the harmonization stage reports a constraint conflict error with language-specific diagnostic messages in each involved language.

Constraint conflict resolution follows the envelope intersection rule: the most restrictive constraint applies. In the Japanese-Spanish example, the Japanese “without fail” constraint prevails over the Spanish “if possible” constraint, because the strict requirement is more restrictive. This resolution is deterministic and language-neutral: it does not favor Japanese over Spanish but rather favors the more conservative specification over the more permissive one.

11.5 Cultural Drift
Cultural drift is the multilingual analogue of semantic drift [11]: changes in a language's programming conventions over time cause the same expression to resolve differently across compiler versions. Cultural drift is particularly pronounced in languages where programming terminology is rapidly evolving. Japanese programming terminology borrows heavily from English (ファイル = “file,” データベース = “database”), and the borrowing conventions shift as new technologies introduce new terminology.

Cultural drift is managed through the same version-locking strategy used for English Mode: each language module's vocabulary tables are frozen at compiler release. Cultural evolution that occurs after the release does not affect compilations under that release. When a new compiler version is released, the updated vocabulary tables reflect current conventions, and the migration analysis tool reports any resolution changes to users.

The version-locking strategy applies equally to all supported languages, ensuring that cultural drift does not introduce cross-lingual divergence. If a Japanese term's mapping changes in a new version, the cross-lingual equivalence corpus test suite detects any divergence from the equivalent English expression's mapping, enabling coordinated updates across language modules.

11.6 Intent Inversion
Intent inversion in multilingual inference occurs when a language's negation structure is mishandled, causing the normalization module to produce the opposite of the intended canonical action. Negation handling varies significantly across languages. English uses pre-verbal negation (“do not delete”). Japanese uses post-verbal negation (削除しない, “sakujo shinai,” verb + negative suffix). Arabic uses pre-verbal negation particles (لا تحذف, “la taħdhif,” negation particle + verb). Mandarin uses pre-verbal negation (不要删除, “bùyào shānchú,” negation + verb).

Each language module implements a language-specific negation detection and propagation system. Japanese negation detection scans for the negative suffixes ない (“nai”), ません (“masen”), and ず (“zu”) following or attached to verb stems. Arabic negation detection scans for the particles لا (“la”), لم (“lam”), and لن (“lan”) preceding verbs. Mandarin negation detection scans for 不 (“bù”), 别 (“bié”), and 不要 (“bùyào”) preceding verbs. Each detection system maps the negated verb to the corresponding canonical negation action (DELETE → PRESERVE, SEND → BLOCK_SEND).

Negation handling is the most extensively tested aspect of each language module. The negation test corpus for each language contains at least 200 negated expressions, including simple negation, double negation, contextual negation, and implicit negation. This extensive testing reflects the severity of intent inversion: a negation mishandling that converts DELETE to PRESERVE is a safety issue, but a negation mishandling that converts PRESERVE to DELETE is a potential data loss event.

13 Security Analysis
13.1 Multilingual Tampering Resistance
Multilingual tampering resistance inherits the certificate-binding mechanisms from the canonical Trust Layer architecture [3]. Every normalization output, every UIS representation, and every compiled AST is hashed (SHA3-256), signed (Ed25519), and chained to the language module's identity certificate. Tampering with any artifact at any pipeline stage changes the hash, invalidates the signature, and breaks the certificate chain.

The multilingual pipeline introduces an additional tamper-detection mechanism: cross-lingual consistency checking. When the same operation is compiled from multiple languages (either intentionally through coordinated operations or incidentally through duplicate submissions), the EQUIVALENCE verification detects any inconsistency between the normalizations. An attacker who tampers with the Japanese normalization of an operation cannot avoid detection if the same operation was also compiled from English, because the tampered Japanese normalization will produce a different UIS hash than the untampered English normalization.

This cross-lingual consistency checking provides a form of multilingual redundancy that strengthens tamper resistance beyond what any single-language pipeline can achieve. The more languages through which an operation is compiled, the more difficult it becomes for an attacker to tamper with the compilation undetected.

13.2 Identity Forgery Resistance
Identity forgery for multilingual compilations inherits the Ed25519 security properties from the Trust Layer certificate infrastructure [3]. Forging a language module's identity requires compromising the module's private key. Forging the compilation's identity requires compromising the compiler's private key. Both keys are managed through the standard Trust Layer key management practices.

Multilingual identity forgery is further mitigated by the language module certification process. Each language module is certified through the designated Ecosystem Governance Authority, receiving an identity certificate that binds the module to a specific language, a specific version, and a specific normalization specification. An attacker who attempts to introduce a forged language module must obtain a valid certificate from the governance authority, which requires passing the determinism verification corpus and the cross-lingual equivalence tests.

The language module certification process provides a natural defense against supply-chain attacks targeting the multilingual pipeline. An attacker cannot modify a language module's vocabulary tables or normalization rules without obtaining a new certificate for the modified module, and the certification process's determinism verification would detect the modifications through test case failures.

13.3 Certificate Forgery Resistance
Certificate forgery resistance for multilingual certificates extends canonical certificate forgery resistance with the UIS consistency check. A forged NORMALIZATION certificate that claims a specific UIS output can be verified by re-normalizing the source expression and comparing the result. If the re-normalization produces a different UIS output, the forgery is detected. This semantic verification complements the cryptographic verification, providing defense beyond mathematical forgery resistance.

The LANGUAGE_ID certificate is verifiable through independent language identification. If a forged LANGUAGE_ID certificate claims that an Arabic expression is English, the independent language identifier will detect the misclassification through Unicode block analysis and vocabulary frequency matching. This independent verification detects language identification forgery through semantic analysis.

The EQUIVALENCE certificate is verifiable through independent equivalence analysis. If a forged EQUIVALENCE certificate claims that two expressions are equivalent, independent compilation and hash comparison will detect the forgery if the expressions produce different UIS hashes. This independent verification prevents forged equivalence claims from masking cross-lingual divergences.

13.4 Replay Attack Mitigation
Replay attacks against multilingual compilations are mitigated through the same nonce-and-monotonic-timestamp mechanism used for English Mode compilations. Each compilation includes a unique nonce derived from the compiler's state hash and the compilation timestamp. The nonce is independent of the source language; the same replay protection applies to all languages.

Multilingual replay attacks have an additional vector: replaying a compilation from one language while claiming it was compiled from another language. This attack is mitigated by the LANGUAGE_ID certificate, which records the detected source language and is bound to the compilation's certificate chain. Replaying a Japanese compilation while claiming it was compiled from English would produce a certificate chain where the LANGUAGE_ID says Japanese but the claimed provenance says English—an inconsistency detectable by any certificate chain validator.

The cross-lingual replay resistance ensures that language switching cannot be used to circumvent replay detection. An attacker who replays a Japanese compilation cannot avoid detection by claiming the repetition is a new English compilation, because the certificate chain's LANGUAGE_ID contradicts the claimed language.

13.5 Governance Abuse Prevention
Governance abuse prevention for multilingual inference extends canonical governance abuse prevention with language-specific protections. The primary multilingual governance abuse vector is vocabulary manipulation: an attacker with governance authority might modify a language module's verb mapping table to remap a benign verb to a dangerous canonical action. This attack is mitigated by the multi-signature requirement for vocabulary updates and by the cross-lingual equivalence corpus, which would detect mapping changes that break cross-lingual consistency.

A second multilingual governance abuse vector is selective language module certification: a compromised governance authority might certify a malicious language module while leaving other modules untouched. This attack is mitigated by the multi-signature requirement for module certification and by the public transparency of all certification events in the Certificate Fabric.

The Evolver's pattern-capture mechanism extends to multilingual governance, tracking per-language governance action patterns and generating alerts when language-specific patterns suggest targeted manipulation. If a specific language module receives disproportionate vocabulary updates or certification changes, the alert system flags the activity for collective governance review.

14 Performance Considerations
14.1 Multilingual Inference Overhead
The LDIR multilingual pipeline introduces overhead relative to English Mode compilation through the language identification stage and the language-specific normalization stage. Language identification adds approximately 0.2 milliseconds (Unicode block analysis plus decision tree evaluation). Language-specific normalization varies by language: English normalization requires approximately 1.5 milliseconds per expression, Japanese normalization requires approximately 2.5 milliseconds (additional morphological segmentation), Arabic normalization requires approximately 2.0 milliseconds (diacritical processing and root extraction), and Mandarin normalization requires approximately 2.2 milliseconds (character tokenization and measure word processing).

The aggregate pipeline overhead for a typical multilingual expression (20-50 tokens, 1-3 actions, non-English language) is approximately 4-7 milliseconds, compared to 3-5 milliseconds for English Mode. The additional 1-2 milliseconds reflect the language identification stage and the slightly higher computational cost of non-English morphological analysis. This overhead is negligible for interactive programming sessions.

The overhead is offset by the elimination of the translation step. Without LDIR Expansions, a non-English-speaking programmer must mentally translate their intent into English before typing. The LDIR Expansion overhead (1-2 milliseconds of additional compilation time) is negligible compared to the cognitive overhead of real-time mental translation (seconds to minutes per expression).

14.2 Arbitration Latency
Multilingual arbitration adds latency when cross-lingual conflicts trigger the inter-language arbitration mechanism. Intra-language arbitration latency is identical to English Mode arbitration: approximately 0.3-0.5 milliseconds per conflict. Inter-language arbitration adds approximately 1.0-2.0 milliseconds for the cross-lingual comparison, the language seniority evaluation, and the extended certificate generation.

Inter-language arbitration is rare in practice: it occurs only when intended-equivalent expressions from different languages produce different UIS representations, which indicates a normalization quality issue that should be addressed through vocabulary table reconciliation. As language modules mature, inter-language arbitration frequency decreases, approaching zero for well-aligned language pairs.

The arbitration latency is bounded: the number of competing interpretations is finite (bounded by the number of active language modules), and the priority rule evaluation terminates at the first successful resolution. The worst-case multilingual arbitration latency is proportional to the number of supported languages, which is known at compiler initialization.

14.3 Distributed Cognition Cost
Distributed multilingual cognition introduces network latency for language-proximate routing. When a Japanese expression is routed from a compilation node to the Tokyo node hosting the Japanese module, the network round trip adds approximately 1-10 milliseconds depending on geographic distance. For language modules hosted on the same node as the compilation, the latency is sub-millisecond.

The distributed cognition cost is mitigated through language module caching: frequently used language modules can be cached locally on compilation nodes, eliminating the network round trip for common languages. The cache is synchronized with the authoritative module instance through certified state deltas, ensuring that cached modules maintain identical behavior.

The net cost of distributed multilingual cognition represents a tradeoff between latency and capability. A single-node deployment with all language modules hosted locally has minimal latency but limited language coverage. A distributed deployment with language modules hosted on specialized nodes has higher latency for remote languages but can support a larger number of languages. The optimal deployment topology depends on the language distribution of the user population.

15 Future Work
15.1 Cross-Vertical Multilingual Inference
Future work will extend LDIR Expansions to support cross-vertical multilingual inference—resolution of expressions that span multiple DAIGS domain verticals and multiple languages simultaneously. A Japanese medical expression that references financial concepts (insurance reimbursement for a medical procedure) requires both Japanese language normalization and cross-vertical semantic grounding (medical domain + financial domain). The current architecture handles each dimension independently; future work will develop integrated cross-vertical multilingual resolution that coordinates both dimensions simultaneously.

Cross-vertical multilingual resolution requires domain-specific verb synonym tables for each language-vertical combination. The table for Japanese-Medical would map medical-specific Japanese verbs to medical canonical actions; the table for Japanese-Financial would map financial-specific Japanese verbs to financial canonical actions. The management and versioning of these per-language-per-vertical tables represents a significant configuration complexity that future work must address through automated table generation and validation.

The long-term vision is a multilingual inference fabric that supports the full DAIGS 22-vertical taxonomy across all supported languages, enabling any human operator in any language to express intent in any domain vertical and receive deterministic, certificate-anchored compilation.

15.2 ZK-Native Multilingual Verification
Future work will integrate zero-knowledge proof systems into the multilingual inference pipeline, enabling language modules to prove the correctness of their normalization without revealing the source expression. This privacy-preserving verification is valuable for multilingual compilations involving sensitive content (medical records, financial transactions, classified communications) where the source expression itself is confidential.

ZK-native multilingual verification requires the development of proof circuits for each language module's normalization pipeline. Each circuit must prove correct morphological analysis, correct verb mapping, correct parameter extraction, and correct UIS emission without revealing the input tokens, the intermediate representations, or the normalization rules. Designing efficient proof circuits for morphologically complex languages (Arabic, Turkish, Finnish) is a significant cryptographic engineering challenge.

The successful implementation of ZK-native multilingual verification will enable confidential cross-lingual compilation: an operator in one jurisdiction can compile a directive in their local language, produce a zero-knowledge-certified executable, and deploy it to another jurisdiction where the governance authority can verify compliance without accessing the original directive in the source language.

15.3 Autonomous Organism Multilingual Cognition
Future work will enable synthetic organisms to formulate behavioral directives in multiple languages and compile them through the LDIR expansion pipeline. Currently, organisms formulate intents through structured data objects. Enabling organisms to formulate intents in natural language would provide cognitive transparency (human-readable intent formulation) for multilingual governance review.

Autonomous multilingual cognition raises the question of which language an organism “thinks in.” The answer, within the LDIR framework, is the Universal Intent Schema: organisms formulate intents in canonical form and express them in the source language most appropriate for the current operational context. A governance review in Japan would receive the organism's intent expressed in Japanese; the same review in Germany would receive it expressed in German. The underlying canonical intent is identical.

The successful implementation of autonomous organism multilingual cognition will, to my knowledge, represent the first instance of a deterministic system capable of expressing computational intent in multiple human languages through a unified, certificate-bound compilation pipeline. This capability opens the research frontier for truly multilingual autonomous systems that operate seamlessly across linguistic and cultural boundaries.

15.4 Global Doctrinal Frameworks
Future work will develop international standards for multilingual deterministic inference. These standards will specify minimum normalization quality, minimum cross-lingual equivalence coverage, minimum negation detection accuracy, and minimum vocabulary table coverage for each supported language. Compliance with these standards will be verifiable through the determinism verification corpus and the cross-lingual equivalence corpus.

Global doctrinal frameworks also require governance harmonization across jurisdictions. Different jurisdictions may impose different requirements on multilingual compilation (requiring specific language modules to be certified by local regulatory authorities, mandating specific cross-lingual equivalence verification for regulated domains). Future work will develop jurisdictional governance composition rules that deterministically resolve conflicts between jurisdiction-specific multilingual requirements.

The long-term objective is a globally recognized LDIR standard that enables regulatory authorities in any jurisdiction to evaluate and certify multilingual compilations against internationally agreed criteria. This standardization will facilitate the deployment of multilingual deterministic systems in regulated industries across national boundaries.

16 Conclusion
The Lume ecosystem was designed to eliminate the cognitive distance between human expression and computational execution. English Mode achieved this elimination for English-speaking programmers. LDIR Expansions extend this achievement to speakers of every supported human language, demonstrating that the deterministic natural-language compilation pipeline is not inherently English-centric but is fundamentally language-independent in its architectural design.

The Universal Intent Schema provides the convergence point that makes multilingual determinism achievable. By requiring all language normalization modules to produce output in a shared, language-independent format, the architecture ensures that the downstream compilation pipeline—AST mapping, envelope derivation, governance validation, certificate emission—operates on representations that carry no language-specific information. This convergence architecture eliminates the risk of language-specific behavior in the runtime, the governance layer, and the certification layer, ensuring that all languages receive identical treatment throughout the execution lifecycle.

The six failure modes identified in this paper—semantic collapse, over-normalization, under-normalization, conflicting constraints, cultural drift, and intent inversion—provide the diagnostic framework for maintaining multilingual inference quality. Each failure mode has a defined detection mechanism, a defined resolution strategy, and a defined testing approach. The cross-lingual equivalence corpus provides the continuous verification infrastructure that detects regressions and identifies normalization quality issues across all supported language pairs.

The integration architecture binds LDIR Expansions to every layer of the Lume ecosystem: the compiler (through the language-routing frontend), the Trust Layer (through certificate-bound language provenance), Lume-V (through language-aware envelope enforcement), DAIGS (through multilingual cognitive substrate extensions), SOR (through cross-lingual organism communication), and GUPAS (through language-independent governance validation). This comprehensive integration ensures that multilingual capabilities are first-class citizens within the governed ecosystem, receiving the same deterministic guarantees, security protections, and governance oversight as English Mode capabilities.

To my knowledge, this paper presents the first complete multilingual inference architecture for a deterministic natural-language programming ecosystem. The architecture demonstrates that the fundamental barriers to multilingual deterministic compilation—semantic drift, cultural variance, ambiguity propagation, and negation handling diversity—can be addressed through structured normalization, universal schema convergence, and cross-lingual equivalence verification, without sacrificing the bit-identical determinism that the Lume ecosystem requires. As the ecosystem extends to serve globally distributed teams, autonomous agents across linguistic boundaries, and synthetic organisms in heterogeneous language environments, LDIR Expansions provide the multilingual substrate on which this global extension is built.

Appendix A — Definitions
A.1 LDIR (Lume Deterministic Inference Relay)
The inference rulebook that governs how natural-language expressions are resolved into deterministic computational directives within the Lume ecosystem. The canonical LDIR contains 31 rules across 4 tiers. LDIR Expansions extend the canonical rulebook with language-specific normalization modules, cross-lingual equivalence verification, and multilingual arbitration rules. The expanded LDIR maintains the canonical tier hierarchy (Tier 4 Safety, Tier 3 Axiom, Tier 2 Domain, Tier 1 Default), with language-specific rules placed at Tier 2 and Tier 1.

A.2 Semantic Equivalence
Two natural-language expressions in different languages are semantically equivalent if and only if they produce identical Universal Intent Schema (UIS) representations when processed through their respective language normalization modules. This definition is computational, not linguistic: it determines whether two expressions produce the same canonical action, not whether they convey the same meaning to human listeners. Semantic equivalence is verified through UIS hash comparison (SHA3-256).

A.3 Intent Tuple
A formal data structure consisting of five fields: intent source (the original expression in the source language), intent hash (SHA3-256 digest of the UIS representation—not of the source-language text), resolved action (the canonical action from the universal action vocabulary), trust binding (the compiler's certificate), and envelope constraint (the safety boundary derived from the UIS). In multilingual compilations, the intent hash is computed from the language-independent UIS representation, ensuring cross-lingual hash identity for semantically equivalent expressions.

A.4 Canonical AST
The deterministic Abstract Syntax Tree produced by the Lume compiler, following a strict construction order (depth-first, left-to-right). The canonical AST is produced from the UIS representation through the language-independent action-to-AST mapping function. Identical UIS representations produce identical canonical ASTs regardless of the source language, by construction.

A.5 Envelope Constraint
A declarative policy bounding execution along four dimensions: resource consumption, state mutation scope, external interaction boundaries, and temporal limits. In multilingual compilations, envelope constraints are derived from the language-independent UIS representation through the standard constraint extraction logic. Language-specific pragmatic modifiers may narrow the derived envelope but may never widen it beyond canonical defaults.

A.6 Certificate Fabric
The directed acyclic graph of cryptographically signed trust assertions in the Trust Layer. Multilingual compilations contribute four certificates: LANGUAGE_ID (source language detection), NORMALIZATION (language module version and UIS output), RESOLUTION (tolerance chain path), and COMPILE_ROOT (AST hash and output hash). An optional EQUIVALENCE certificate records cross-lingual hash comparisons.

A.7 Deterministic Transition Graph
A directed graph representing state evolution, where each node is a committed state (SHA3-256 hash) and each edge is an intent-triggered transition. In multilingual contexts, the graph's edges reference Intent Tuples whose source fields preserve the original expression in the source language, enabling multilingual forensic reconstruction of state evolution.

A.8 Arbitration Layer
The compile-time mechanism that resolves competing interpretations of ambiguous expressions. In multilingual compilation, the Arbitration Layer handles both intra-language conflicts (multiple interpretations within one language) and inter-language conflicts (divergent UIS representations from different language modules for intended-equivalent expressions). The priority hierarchy is: safety, specificity, canonical precedence, language seniority, and envelope safety.

Appendix B — Algorithms
B.1 Multilingual Normalization Algorithm
Algorithm MultilingualNormalization:
Input: RawExpression, CompilerCertificate
Output: UIS_Representation, LanguageID, NormalizationCertificate

 1: DETECT script via Unicode block analysis
 2: IF script unambiguous (CJK, Arabic, Devanagari):
 3:    language = script_to_language_map[script]
 4: ELSE (Latin, Cyrillic, etc.):
 5:    language = decision_tree_classify(n_gram_features(RawExpression))
 6: LOAD language_module = module_registry[language]
 7: VERIFY language_module.certificate chain to ecosystem root
 8: IF certificate invalid: REJECT (MODULE_UNAUTHORIZED)
 9: EMIT LANGUAGE_ID certificate (language, detection_features)
10: APPLY language_module.lexical_normalization(RawExpression):
11:    Japanese: morphological_segmentation + particle_identification
12:    Arabic: diacritical_normalization + root_extraction
13:    Mandarin: character_tokenization + measure_word_identification
14:    Spanish: clitic_analysis + diacritical_preservation
15:    English: standard English Mode normalization
16: APPLY language_module.semantic_grounding:
17:    MAP verbs via language.verb_synonym_table → canonical actions
18:    MAP objects via language.object_keyword_table → canonical objects
19:    MAP modifiers via language.modifier_table → canonical modifiers
20: APPLY language_module.negation_detection:
21:    DETECT language-specific negation markers
22:    PROPAGATE negation to canonical action (DELETE → PRESERVE)
23: EMIT UIS_Representation in Universal Intent Schema format
24: VALIDATE UIS contains only canonical vocabulary
25: COMPUTE uis_hash = SHA3-256(UIS_Representation)
26: EMIT NormalizationCertificate (module_version, input_hash, uis_hash)
27: RETURN (UIS_Representation, language, NormalizationCertificate)
B.2 Semantic Equivalence Algorithm
Algorithm CrossLingualEquivalence:
Input: UIS_A (from language A), UIS_B (from language B)
Output: EQUIVALENT or DIVERGENT, EquivalenceCertificate

 1: COMPUTE hash_A = SHA3-256(UIS_A)
 2: COMPUTE hash_B = SHA3-256(UIS_B)
 3: IF hash_A == hash_B:
 4:    result = EQUIVALENT
 5:    EMIT EquivalenceCertificate (language_A, language_B, MATCH, hash_A)
 6: ELSE:
 7:    result = DIVERGENT
 8:    IDENTIFY divergence fields:
 9:       COMPARE UIS_A.action vs UIS_B.action
10:       COMPARE UIS_A.parameters vs UIS_B.parameters
11:       COMPARE UIS_A.modifiers vs UIS_B.modifiers
12:    EMIT EquivalenceCertificate (language_A, language_B, MISMATCH, 
         divergence_fields, hash_A, hash_B)
13:    LOG divergence for language module reconciliation
14: RETURN (result, EquivalenceCertificate)
B.3 Cross-Lingual Constraint Extraction Algorithm
Algorithm CrossLingualConstraintExtraction:
Input: UIS_Representation, ExecutionContext, PragmaticModifiers
Output: EnvelopeConstraints

 1: EXTRACT base constraints from UIS using standard extraction logic
 2: FOR each pragmatic modifier P in PragmaticModifiers:
 3:    IF P.type == STRICTNESS (e.g., Japanese 必ず):
 4:       NARROW reliability envelope (increase minimum reliability)
 5:    IF P.type == CONDITIONALITY (e.g., Spanish "si es posible"):
 6:       FLAG as conditional but DO NOT WIDEN envelope
 7:    IF P.type == URGENCY:
 8:       NARROW temporal envelope (reduce maximum duration)
 9: INTERSECT derived constraints with ExecutionContext.envelope:
10:    final = intersection(derived, context.envelope)
11: VALIDATE: final ⊆ context.envelope (never wider)
12: RETURN final EnvelopeConstraints
B.4 Arbitration Algorithm
Algorithm MultilingualArbitration:
Input: CompetingInterpretations[], SourceLanguages[], EnvelopeConstraints
Output: SelectedInterpretation, ArbitrationCertificate

 1: FILTER: Remove interpretations violating EnvelopeConstraints
 2: IF single interpretation remains: SELECT it, CERTIFY, RETURN
 3: CLASSIFY conflict type:
 4:    IF all interpretations from same language: INTRA_LANGUAGE
 5:    ELSE: INTER_LANGUAGE
 6: EVALUATE safety (Tier 4 violations eliminate candidates)
 7: EVALUATE specificity (parameter count scoring)
 8: IF unique winner: SELECT, CERTIFY, RETURN
 9: EVALUATE canonical precedence (action ordinal in universal vocabulary)
10: IF unique winner: SELECT, CERTIFY, RETURN
11: IF INTER_LANGUAGE:
12:    EVALUATE language seniority (pattern database depth per language)
13:    IF unique winner: SELECT, CERTIFY, RETURN
14: APPLY safety tiebreaker: SELECT smallest envelope footprint
15: CONSTRUCT ArbitrationCertificate:
16:    Record competing interpretations, languages, scores, selected
17: SIGN with compiler Ed25519 key
18: RETURN (SelectedInterpretation, ArbitrationCertificate)

The INTRA_LANGUAGE branch follows the standard priority rules (Specificity → Precedence → Context → Safety). The INTER_LANGUAGE branch follows the extended priority rules (Safety → Specificity → Canonical Precedence → Language Seniority → Envelope Safety). Each terminal node emits a multilingual Arbitration Certificate recording the conflict type, the languages involved, and the resolution path.

Appendix D — Implementation Notes
D.1 Grammar Primitives
Each language module defines grammar primitives that map the language's grammatical structures to UIS structures. The primitive vocabulary includes language-specific verb lists (mapped to the 47 canonical action verbs), language-specific object keyword lists (mapped to the 23 canonical object types), and language-specific modifier categories (mapped to the 15 canonical modifier types). Each language's grammar primitives are published in the module's specification document and audited during the certification process.

D.2 Deterministic Parsing Rules
Parsing rules for each language are implemented as deterministic finite automata tailored to the language's syntactic structure. Japanese parsing uses SOV-order DFAs that scan for the verb at the sentence end and identify objects and modifiers in the preceding positions. Arabic parsing uses VSO-order DFAs that identify the verb at the sentence beginning and scan for subject and object in the following positions. Each language's DFAs are version-locked and loaded as read-only data structures at compiler initialization.

D.3 Integration with Lume Runtime
Multilingual compilation integrates with the Lume runtime through the same compile(source) -> AST API used by English Mode. The runtime does not distinguish between ASTs from different language frontends. The language-routing decision occurs within the compilation frontend, before the AST is emitted. The runtime receives a language-independent canonical AST and executes it according to standard deterministic semantics.

D.4 Trust Layer Hooks
Multilingual compilation invokes four Trust Layer hooks: issue_language_id_cert(language, features) after language detection, issue_normalization_cert(module_version, input_hash, uis_hash) after normalization, issue_resolution_cert(path, uis_hash) after tolerance chain traversal, and issue_compile_cert(ast_hash, output_hash) after AST mapping. An optional fifth hook, issue_equivalence_cert(lang_A, lang_B, result, hashes), is invoked during cross-lingual equivalence verification.

D.5 Lume-V Wrapper Requirements
Lume-V wrappers for multilingual compilations implement the standard envelope enforcement interface without language-specific extensions. The wrapper receives the envelope constraints derived from the UIS representation and configures its enforcement parameters. The wrapper does not perform language-specific analysis. The behavioral profile is derived from the UIS's canonical action types, ensuring language-independent monitoring and enforcement.

Appendix E — Governance & Compliance
E.1 Who Can Declare Multilingual Intent
Multilingual intent declaration is restricted to entities possessing valid identity certificates with the INTENT_DECLARE capability. The capability is language-independent: an entity authorized to declare intent in English is authorized to declare intent in any supported language. Language-specific authorization restrictions can be introduced through Governance Expansion Subsystem policies [10] (for example, requiring that intent declaration in a regulated domain's language be authorized by a domain-specific compliance officer).

Language module development and maintenance is restricted to entities possessing the LANGUAGE_MODULE_DEVELOP capability, which is a specialized capability granted by the designated Ecosystem Governance Authority. This capability restriction ensures that only qualified linguists and engineers can modify the normalization tables and parsing rules that govern multilingual compilation.

E.2 How Multilingual Arbitration Is Governed
Multilingual arbitration is governed through the same GUPAS governance framework used for English Mode arbitration. Arbitration rules are certified through the Trust Layer and deployed through the standard expansion lifecycle. Language-specific arbitration rules require domain expert review to ensure that they do not introduce language-based bias. The cross-lingual fairness constraint (§9.2) is verified through statistical analysis of arbitration outcomes across language pairs.

Inter-language arbitration rules require additional governance scrutiny. Because these rules determine the outcome of conflicts between different languages' normalization modules, they have the potential to systematically favor one language over another. The governance review process for inter-language arbitration rules includes impact analysis across all language pairs, ensuring that the rule does not introduce systematic bias.

E.3 Safety Rules
Multilingual safety rules extend the canonical LDIR Tier 4 with language-universal constraints: ML-01 (Negation Must Be Detected and Propagated in Every Supported Language), ML-02 (Normalization Must Not Invert Intent in Any Language), ML-03 (UIS Output Must Contain Only Canonical Vocabulary), ML-04 (Cross-Lingual Equivalence Must Be Verified for Coordinated Operations), and ML-05 (Language Module Certificate Must Be Valid and Unrevoked). These rules are hard-coded and cannot be modified through governance policies.

E.4 Interaction with Proof-of-Intent
Multilingual compilations produce Intent Tuples whose source fields preserve the original expression in the source language. The Proof-of-Intent mechanism [13] can therefore trace any execution outcome back to the original human-language expression, in the language in which the human operator expressed it. This native-language provenance is valuable for regulatory compliance in jurisdictions that require documentation in the local language.

The PoI mechanism treats multilingual Intent Tuples identically to English Mode Intent Tuples. The proof evaluates the canonical action (from the UIS) against the execution outcome, verifying that the outcome is consistent with the declared intent. The evaluation is language-independent, ensuring consistent PoI quality across all source languages.

Appendix F — Extended Examples
F.1 Example Multilingual Inference
A Japanese programmer writes: 売上データベースから顧客レコードを読み込んで、地域別の総売上レポートを作成してください (“Please read customer records from the sales database and create a total revenue report by region”). The language identification stage detects Japanese through CJK script analysis. The Japanese normalization module performs morphological segmentation, identifying verb stems 読み込む (READ) and 作成する (CREATE), objects 顧客レコード (customer records) and レポート (report), and modifiers 地域別 (by region). The normalization produces UIS: SEQUENCE[READ(source="sales_database", filter="customer_records"), CREATE(type="report", template="summary", grouping="region", metric="revenue")].

An English programmer writes the equivalent: “Read the customer records from the sales database and create a summary report showing total revenue by region.” The English Mode pipeline produces the identical UIS representation. The cross-lingual equivalence verification compares the SHA3-256 hashes: they match. The EQUIVALENCE certificate records the match, confirming cross-lingual determinism for this expression pair.

F.2 Example Arbitration Scenario
A Spanish programmer writes: “Actualizar los datos del sistema” (“Update the system data”). A German programmer writes the intended equivalent: “Systemdaten aktualisieren” (“Update system data”). The Spanish module maps “actualizar” to UPDATE. The German module maps “aktualisieren” to UPDATE. Both produce UIS: UPDATE(target="system_data"). The hashes match; no arbitration is needed.

Now consider a conflict: a Portuguese programmer writes “Atualizar os dados do sistema” but the Portuguese module, being newly deployed, maps “atualizar” to REFRESH instead of UPDATE. The cross-lingual equivalence verification detects the hash mismatch. Inter-language arbitration activates. The arbitration evaluates canonical precedence: UPDATE (ordinal 3) takes precedence over REFRESH (ordinal 28). UPDATE is selected. The Arbitration Certificate records the divergence and recommends reconciliation of the Portuguese verb table.

F.3 Example Certificate-Bound Multilingual Intent
An autonomous compliance agent operating in Japan compiles: ￥10,000を超える全ての取引をコンプライアンスレビューのためにフラグを立ててください (“Please flag all transactions exceeding ¥10,000 for compliance review”). The compilation produces four certificates: LANGUAGE_ID (Japanese, confidence 1.0), NORMALIZATION (Japanese module v1.0.0, UIS hash matching), RESOLUTION (Layer 1 exact match), and COMPILE_ROOT (AST hash, output hash). The certificate chain provides a complete, cryptographically verifiable record that a specific Japanese expression was compiled into a specific compliance flagging action through the Japanese LDIR pipeline.

Appendix G — Threat Models
G.1 Malicious Multilingual Injection
An attacker crafts an expression that appears benign in one language but resolves to a harmful action through the LDIR pipeline. For example, the attacker uses a Japanese homograph attack: a string that appears to be the Japanese word for “save” (保存, “hozon”) but actually contains visually similar Unicode characters from a different script that map to “delete” in the other script's normalization module.

This attack is mitigated by the language identification stage, which detects script inconsistencies through Unicode block analysis. A string containing characters from multiple scripts triggers a mixed-script warning, and the compilation proceeds only if the mixed-script expression matches a known legitimate pattern (such as Japanese text containing Latin-script technical terms). Unrecognized mixed-script patterns are rejected with a security diagnostic.

The homograph attack is further mitigated by the normalization module's vocabulary table, which maps only recognized linguistic forms to canonical actions. A visually similar character sequence that is not in the vocabulary table fails verb identification and is routed to the AI fallback layer, which evaluates it against the language's legitimate vocabulary. Fabricated character sequences that do not exist in the language's vocabulary are rejected as unrecognizable.

G.2 Semantic Manipulation
An attacker exploits cross-lingual semantic differences to manipulate arbitration outcomes. The attacker submits two versions of the same operation in different languages, knowing that the normalization modules will produce different canonical actions and that the arbitration priority rules will select the attacker's preferred action.

This attack is mitigated by the cross-lingual fairness constraint and the arbitration transparency. The Arbitration Certificate records both competing interpretations, enabling post-hoc review. If a pattern of manipulative submissions is detected (the same entity consistently submitting conflicting cross-lingual expressions), the governance authority can investigate and impose corrective measures.

The attack is further mitigated by the vocabulary table reconciliation feedback loop. Systematic divergences between language modules' canonical action mappings are detected by the Evolver and flagged for reconciliation. As language modules mature and their mappings converge, the opportunity for semantic manipulation through cross-lingual divergence diminishes.

G.3 Governance Manipulation
An attacker with governance authority manipulates a language module's vocabulary table to remap verbs in a way that benefits the attacker. This attack is mitigated by the multi-signature requirement for vocabulary updates, the determinism verification corpus (which detects mapping changes through test case failures), and the cross-lingual equivalence corpus (which detects mapping changes that break cross-lingual consistency).

Targeted governance manipulation against a specific minority language (modifying the vocabulary table for a language with few speakers, who may not notice the change) is mitigated by the automated cross-lingual consistency monitoring. Even if no human speaker reviews the minority language module, the automated equivalence verification detects any mapping change that causes the minority language to diverge from the majority languages' mappings.

This automated protection for minority languages is a critical governance safeguard. Without it, languages with fewer speakers and fewer module maintainers would be vulnerable to governance manipulation that would not be attempted against major languages with active maintainer communities.

Appendix H — Formal Notation
H.1 Multilingual Intent Notation
A multilingual Intent Tuple is formally represented as a sextuple IL = (s, L, h, a, c, e) where s ∈ ΣL* is the intent source (a string over the language-specific alphabet ΣL), L ∈ ℒ is the source language identifier (from the set of supported languages ℒ), h = SHA3-256(UIS(NL(s))) is the intent hash (computed from the UIS representation of the language-specific normalization of the source), a = AST(UIS(NL(s))) is the resolved action (the canonical AST mapped from the UIS), c ∈ 𝓞 is the trust binding (a certificate from the certificate space), and e = E(UIS(NL(s)), C) is the envelope constraint (derived from the UIS and the execution context C). The multilingual determinism invariant requires: ∀ s1 ∈ ΣL1*, s2 ∈ ΣL2*: UIS(NL1(s1)) = UIS(NL2(s2)) ⇒ h(s1) = h(s2) ∧ a(s1) = a(s2).

H.2 Semantic Equivalence Equations
Two expressions s1 ∈ ΣL1* and s2 ∈ ΣL2* are semantically equivalent, written s1 ≡UIS s2, if and only if UIS(NL1(s1)) = UIS(NL2(s2)). The equivalence relation is reflexive (s ≡UIS s), symmetric (s1 ≡UIS s2 ⇒ s2 ≡UIS s1), and transitive (s1 ≡UIS s2 ∧ s2 ≡UIS s3 ⇒ s1 ≡UIS s3), forming a proper equivalence relation on the union of all language expression spaces. The equivalence class [s]UIS = {s' ∈ ΣL* : ∃ L ∈ ℒ, UIS(NL(s')) = UIS(NL0(s))} represents all expressions in all languages that produce the same computational action.

H.3 Envelope Rules
The multilingual envelope derivation function EML: UIS × P × C → 𝔼 maps a UIS representation, a set of pragmatic modifiers P, and an execution context C to an envelope 𝔼. The derivation follows the base-plus-pragmatic rule: 𝔼 = Ebase(UIS) ∩ Epragmatic(P) ∩ C.envelope, where Ebase is the standard constraint extraction from the UIS and Epragmatic applies the language-specific pragmatic modifiers. The pragmatic envelope follows the one-directional rule: Epragmatic(P) ⊆ Edefault (pragmatic modifiers narrow, never widen). The final envelope satisfies: 𝔼 ⊆ Ebase(UIS) ∩ C.envelope (the multilingual envelope is at least as restrictive as the base envelope intersected with the context envelope).
